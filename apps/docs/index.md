## 왜 Arche 인가

회사의 정책과 보고서, 매뉴얼, 계약서는 수백 개로 흩어져 있습니다. 어려운 질문일수록 정답은 한 문서가 아니라 여러 문서에 걸친 관계 안에 숨어 있습니다. 지금 흔히 쓰는 두 방식은 저마다 약점이 뚜렷합니다.

문서를 통째로 AI 에 밀어 넣으면(full-context, 문서 전체를 한 번에 모델에 넣는 방식) 토큰 비용이 폭증하고 느립니다. 문서가 많으면 애초에 다 들어가지도 않습니다. 청크 벡터 검색(chunk RAG, 문서를 토막 내 비슷한 토막을 찾아 쓰는 방식)은 닮은 토막은 잘 찾지만 관계를 잇지 못합니다. 여러 단계를 건너뛰는 질문이나 표 속 숫자 비교에서 무너집니다.

Arche 는 문서를 미리 관계 지도(그래프)로 바꿔 둡니다. AI 에이전트는 MCP 로 붙어 그 위에서 문서를 넣고, 작고 값싼 조회만으로 답에 필요한 연결을 따라갑니다. 에이전트를 쓰지 않고 사람이 직접 부르는 저수준 REST API 도 열려 있지만, 기본 통로는 MCP 입니다.

## 검증된 가치

조건을 맞춰(같은 AI 모델, 같은 에이전트 방식) 비교했을 때, FinanceBench(재무 보고서 기반 질문 묶음)에서 Arche 그래프 단독은 **94-97%**, 대표적 외부 그래프 도구(graphify)는 **57.6%** 였습니다. 차이를 만든 건 모델 크기가 아니라 문서의 관계와 숫자를 그래프에 얼마나 빠짐없이 담았느냐입니다. 측정 방법·재현 절차·도메인별 한계는 [왜 그래프인가](/concepts/why-graph)에서 다룹니다.
