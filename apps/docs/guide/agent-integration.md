# 에이전트에 연결하기

Arche 를 쓰는 가장 기본 통로는 MCP 입니다. AI 에이전트가 MCP 로 Arche 에 붙어, 문서를 그래프에 넣고 그 그래프에 질의합니다. 에이전트는 사용자의 질문을 받아 도구를 몇 번 부르고, 돌아온 점과 선을 읽어 답을 조립합니다. 이 장은 그 연결을 처음부터 끝까지 짚습니다.

MCP(Model Context Protocol)는 AI 에이전트가 외부 도구를 표준 방식으로 부르게 해 주는 규약입니다. 도구마다 이름과 입력 형식이 정해져 있고, 에이전트는 그 규격대로 호출만 하면 됩니다. Arche 는 문서를 넣는 적재 도구와 그래프를 읽는 조회 도구를 모두 MCP 로 노출하므로, MCP 를 말할 줄 아는 에이전트라면 별도 연동 코드 없이 하나의 연결로 문서를 넣고 그래프를 질의합니다. 사람이 에이전트를 쓰지 않고 직접 부르는 저수준 REST API 는 [문서를 그래프에 넣기](/guide/ingest)와 [그래프에 질의하기](/guide/query)에서 따로 다룹니다.

## MCP 서버 띄우기

::: warning 먼저 환경이 준비돼 있어야 합니다
이 아래 내용은 그래프 DB(Neo4j)와 `.env` 가 이미 준비된 상태를 전제합니다. `arche mcp serve` 로 띄운 MCP 서버는 그래프 DB 에 **직접** 붙고(API 서버를 거치지 않습니다), 문서를 넣을 때는 `.env` 의 AI 모델 키를 씁니다. 아직 안 띄웠다면 [시작하기](/guide/getting-started)로 Neo4j 를 올리고 키를 채운 뒤 돌아오세요.
:::

Arche 저장소 안에서 아래 명령으로 MCP 서버를 띄웁니다.

```bash
uv run --project apps/api arche mcp serve --stdio
```

`--stdio` 는 전송 방식을 가리킵니다. 서버와 에이전트가 프로세스의 표준 입력과 표준 출력(standard input/output, 줄여서 stdio)으로 메시지를 주고받는다는 뜻입니다. 에이전트 쪽이 이 명령을 자식 프로세스로 실행하고 그 입출력에 붙어 대화합니다. 그래서 보통은 이 명령을 손으로 직접 실행하지 않고, 다음 절처럼 에이전트 설정에 적어 두면 에이전트가 알아서 띄웁니다.

::: tip 전송 방식 두 가지
붙는 방식은 두 가지입니다. 어느 쪽이든 노출하는 도구와 응답은 같습니다.

- **stdio** — 에이전트와 Arche 가 **같은 기계**에 있을 때 씁니다. 위 `arche mcp serve --stdio` 가 이 방식입니다. 에이전트가 서버를 자식 프로세스로 띄워 표준 입출력에 붙습니다. 설정이 가장 간단해 로컬 개발에 잘 맞습니다.
- **HTTP(SSE) / Streamable HTTP** — **네트워크 너머** 원격이나 클라우드에서 도는 에이전트가 붙을 때 씁니다. 이건 `arche mcp serve` 가 아니라 API 서버가 띄웁니다. 아래 [원격에서 붙기](#원격에서-붙기-http-전송)에서 다룹니다.

`arche mcp serve` 자체는 stdio 전용 진입점이라, `--no-stdio` 로는 HTTP 를 띄우지 않고 명시적으로 안내만 하고 멈춥니다. HTTP 는 API 서버 쪽 경로를 쓰세요.
:::

`arche mcp serve --stdio` 로 띄운 서버는 도구 열 개를 모두 노출합니다. 그래프를 읽는 조회 도구 여섯 개와 문서를 그래프에 넣는 검토형 적재 도구 네 개가 함께 올라옵니다. 그래서 에이전트는 이 MCP 연결 하나로 문서 적재와 그래프 질의를 둘 다 처리합니다. CLI 의 `arche ingest <폴더>` 나 REST 의 `POST /admin/ingest` 는 에이전트 없이 문서를 직접 넣을 때 쓰는 저수준 방법입니다(자세한 흐름은 [문서를 그래프에 넣기](/guide/ingest) 참고). 어느 도구가 노출되는지는 아래 [도구 이름표](#도구-이름표)에서 정리합니다.

## 에이전트에 등록하기

에이전트(클라이언트) 쪽에는 이 서버를 어떻게 띄울지 한 조각만 적어 주면 됩니다. 저장소를 클론해 쓴다면 아래 형태를 권합니다. 저장소 경로를 직접 가리켜서, 별도 설치 없이 그 저장소의 `.env`(시작하기에서 채운 그 파일)를 그대로 씁니다. Claude Desktop 을 예로 들면 설정 파일에 다음을 더합니다.

```json
{ "mcpServers": { "arche": { "command": "uv", "args": ["run", "--project", "/path/to/arche/apps/api", "arche", "mcp", "serve", "--stdio"] } } }
```

`/path/to/arche` 를 실제로 내려받은 경로로 바꿔 적으면 됩니다. 에이전트는 이 설정을 읽어 명령을 자식 프로세스로 띄우고, 그 표준 입출력에 붙어 도구 목록을 받아 옵니다.

`arche` 를 명령으로 바로 부르고 싶다면 전역에 설치할 수도 있습니다. 저장소 안에서 `uv tool install ./apps/api` 를 한 번 돌리면 `arche` 가 실행 경로(PATH)에 올라, `command` 를 `"arche"` 로 짧게 적을 수 있습니다. 다만 이때는 실행 폴더가 정해지지 않아 `.env` 를 못 찾을 수 있으니, 접속 정보를 아래 [접속 정보(키)를 어떻게 넘기나](#접속-정보-키-를-어떻게-넘기나)의 `env` 블록으로 직접 넘기세요.

```json
{ "mcpServers": { "arche": { "command": "arche", "args": ["mcp", "serve", "--stdio"] } } }
```

이 설정을 적는 파일은 클라이언트마다 정해져 있습니다. Claude Desktop 은 아래 파일을 열어(없으면 새로 만들어) `mcpServers` 항목을 더합니다.

- **macOS** — `~/Library/Application Support/Claude/claude_desktop_config.json`
- **Windows** — `%APPDATA%\Claude\claude_desktop_config.json`

파일을 저장한 뒤 Claude Desktop 을 완전히 껐다 다시 켜야 설정이 반영됩니다. 다시 켜면 대화창의 도구 목록에 Arche 도구가 올라옵니다. 안 올라오면 대개 셋 중 하나입니다. 설정 파일의 JSON 문법이 틀렸거나(쉼표/괄호), `command` 의 경로가 맞지 않거나, 접속 정보(`.env` 또는 `env` 블록)가 없어 서버가 뜨자마자 죽은 경우입니다. Claude Desktop 의 MCP 로그(설정 화면의 로그 보기)에서 `arche` 서버의 오류 메시지를 확인하면 원인이 잡힙니다. Cursor 같은 다른 MCP 클라이언트도 형식만 조금 다를 뿐 적는 값은 같습니다. 서버를 어떤 명령으로 띄울지, 접속 정보를 어떻게 넘길지 알려 주는 것이 전부입니다.

### 접속 정보(키)를 어떻게 넘기나

에이전트가 띄운 `arche` 프로세스도 그래프 DB 주소와 AI 모델 키가 있어야 합니다. 두 가지 방법이 있습니다.

- **`.env` 파일** — `arche` 는 실행된 작업 폴더의 `.env` 를 읽습니다. 위 두 번째 형태처럼 `--project /path/to/arche/apps/api` 로 저장소를 가리키면, 그 저장소의 `.env`(시작하기에서 채운 그 파일)를 그대로 씁니다. 로컬에서 가장 간단한 방법입니다.
- **`env` 블록** — 클라이언트 설정에서 프로세스에 환경 변수를 직접 넘길 수도 있습니다. `.env` 를 두기 어려운 환경(전역 설치형 등)에서 씁니다.

```json
{
  "mcpServers": {
    "arche": {
      "command": "arche",
      "args": ["mcp", "serve", "--stdio"],
      "env": {
        "NEO4J_URI": "bolt://localhost:7687",
        "NEO4J_USER": "neo4j",
        "NEO4J_PASSWORD": "arche",
        "OPENAI_API_KEY": "sk-..."
      }
    }
  }
}
```

넘겨야 할 변수의 전체 목록과 기본값은 [환경 변수](/reference/configuration)에 있습니다. `OPENAI_API_KEY` 는 문서를 넣는 적재 도구가 추출과 임베딩에 씁니다. 조회만 할 거라면 그래프 DB 접속 정보(`NEO4J_*`)만 있어도 도구는 뜹니다.

## 원격에서 붙기 (HTTP 전송)

에이전트가 다른 기계나 클라우드에서 돌아 Arche 를 자식 프로세스로 띄울 수 없다면, 네트워크 너머로 붙는 HTTP 전송을 씁니다. 이건 `arche mcp serve` 가 아니라 **API 서버**가 띄웁니다. API 서버를 올리면 MCP 도구가 `/mcp/v1` 주소에 자동으로 함께 마운트됩니다.

```bash
uv run --project apps/api uvicorn arche_api.main:app --host 127.0.0.1 --port 8000
```

여기서 `--host 127.0.0.1` 은 이 기계에서만 접속을 받습니다. 다른 기계에서 붙게 하려면 `0.0.0.0` 으로 바꾸는데, 그러면 **같은 네트워크의 모든 호스트**에 API 가 열립니다. Arche 는 자체 인증이 없으므로 `0.0.0.0` 노출은 아래 경고대로 반드시 프록시 뒤에서만 하세요.

올라오는 주소는 세 개입니다.

| 주소 | 방식 | 하는 일 |
| --- | --- | --- |
| `POST /mcp/v1/` | Streamable HTTP (기본) | 한 주소가 요청과 스트리밍 응답을 함께 처리 |
| `GET /mcp/v1/sse` | HTTP+SSE (레거시) | 서버 → 에이전트 방향 이벤트 스트림 |
| `POST /mcp/v1/message` | HTTP+SSE (레거시) | 에이전트 → 서버 방향 입력 |

에이전트 프레임워크가 Streamable HTTP 를 지원하면 `POST /mcp/v1/` 하나만 있으면 됩니다. 예전 방식만 지원하면 `GET /sse` 와 `POST /message` 짝을 씁니다.

인증과 namespace 는 `Authorization` 헤더로 넘깁니다. 시제품 단계 토큰은 `ns:<namespace>` 형태입니다. 예를 들어 `Authorization: Bearer ns:work-a` 로 부르면 그 호출은 `work-a` namespace 안만 봅니다. 헤더가 없으면 `default` 로 떨어지고, 형식이 어긋난 토큰은 `not_authorized` 로 거부됩니다.

HTTP 전송도 stdio 와 **같은 도구 열 개**를 노출합니다. 조회 여섯 개와 검토형 적재 네 개가 그대로 올라오므로, 원격 에이전트도 이 연결 하나로 문서를 넣고 질의합니다. 어느 전송을 쓰든 도구 이름과 입출력은 같습니다.

::: warning 네트워크에 열기 전에 — 인증과 암호화
HTTP 전송을 열면 검토형 적재 도구(문서를 그래프에 넣는 네 개)까지 네트워크 너머로 열립니다. 두 가지를 반드시 앞단에서 챙기세요.

- **인증** — 시제품 단계의 `ns:<namespace>` 토큰은 접근을 namespace 로 가르기만 할 뿐 그 자체로는 강한 인증이 아닙니다. 게이트웨이나 사내 인증(SSO) 뒤에 두어 실제 인증을 거세요.
- **전송 암호화(TLS)** — 위 예시는 평문 HTTP 입니다. 평문으로 노출하면 `ns:` 토큰과 문서 내용이 회선에서 그대로 새어 나갑니다. HTTPS/TLS 를 종단하는 리버스 프록시(nginx 등) 뒤에 두고, Arche 자체는 프록시만 바라보는 로컬 주소로 묶으세요.
:::

## 도구 이름표

MCP 로 노출되는 도구는 두 묶음입니다. 그래프를 읽기만 하는 조회 도구 여섯 개와 문서를 그래프에 넣는 검토형 적재 도구 네 개입니다. `arche mcp serve --stdio` 로 서버를 띄우면 이 열 개가 한꺼번에 올라옵니다. 검토형 적재 도구가 있으므로 에이전트는 MCP 하나로 문서를 넣고 다시 그 그래프에 질의합니다. 다만 검토형 적재를 거치지 않고 그래프를 직접 바꾸는 쓰기 동작(점 생성, 관계 삭제 등)은 MCP 에 아예 노출하지 않습니다. 에이전트가 사람의 검토 없이 그래프를 함부로 고치지 못하게 막은 것입니다.

조회 도구 여섯 개입니다.

| 도구 | 하는 일 |
| --- | --- |
| `get_schema` | 그래프에 어떤 종류의 점과 선이 있는지, 타입별로 몇 개인지 개요를 본다. |
| `find_entities` | 키워드로 출발점이 될 노드를 찾는다. 거의 모든 질의가 여기서 시작한다. |
| `get_entity` | 노드 하나의 상세와 타입별 인접 관계 수를 본다. |
| `get_neighbors` | 한 노드에서 N 단계 안에 닿는 이웃을 펼친다. |
| `find_path` | 두 노드 사이를 잇는 짧은 경로 몇 개를 찾는다. |
| `get_subgraph` | 여러 출발점 주변을 한꺼번에 펼쳐 하나로 합친다. |

검토형 적재 도구 네 개입니다. 이 넷도 `arche mcp serve --stdio` 로 띄운 서버에 조회 도구와 함께 올라오므로, 에이전트는 같은 MCP 연결로 문서를 넣습니다. 에이전트를 쓰지 않고 사람이 직접 넣을 때는 CLI 의 `arche ingest` 나 REST 의 `POST /admin/ingest` 라는 저수준 방법도 있습니다([문서를 그래프에 넣기](/guide/ingest) 참고). 아래 표는 도구의 모양과 순서를 정리한 참조용입니다. 이 넷은 정해진 차례(계획 → 미리 보기 → 질문 해소 → 확정)로만 써야 합니다.

| 도구 | 하는 일 |
| --- | --- |
| `ingest_plan` | 파일 하나의 변화를 계획만 하고 그래프에는 쓰지 않는다. 계획 번호를 돌려준다. |
| `ingest_preview` | 계획 번호로 바뀔 내용을 항목별로 펼쳐 사람이 검토하게 한다. |
| `ingest_resolve` | 미리 보기가 물은 질문(닮은 점을 합칠지 따로 둘지)에 사람의 결정을 반영한다. |
| `ingest_commit` | 사람이 확인한 계획을 그제야 그래프에 반영한다. |

조회 도구 여섯 개는 REST 에도 같은 주소가 있어 입력과 출력이 그대로 대응합니다. 검토형 적재 도구 네 개는 MCP 로만 노출되고 똑같이 대응하는 REST 주소는 없습니다(REST 로 문서를 넣는 건 `POST /admin/ingest` 라는 별도 경로입니다). 어느 쪽이든 도구가 받는 값과 돌려주는 모양은 [그래프 조회 연산](/reference/primitives) 참조표에 정의된 그대로이고, MCP 와 REST 를 가르는 차이는 딱 하나, **응답 봉투**입니다. REST 는 성공 결과를 `{ "data": ... }` 로 한 겹 감싸 돌려주지만, MCP 는 그 안의 payload 만 봉투 없이 그대로 돌려줍니다. 예를 들어 `find_entities` 를 부르면 REST 는 이렇게 옵니다.

```json
{ "data": { "matches": [ { "node": { "...": "..." }, "score": 1.0 } ] } }
```

같은 호출을 MCP 로 하면 `data` 껍질이 없습니다.

```json
{ "matches": [ { "node": { "...": "..." }, "score": 1.0 } ] }
```

실패도 마찬가지로 봉투 없이 옵니다. MCP 응답에는 오류 표시 플래그가 함께 서고, 본문은 `{ "error": { "code": ..., "message": ..., "details": ... } }` 모양입니다. 조회 도구 여섯 개가 받는 입력 필드와 돌려주는 필드는 [그래프 조회 연산](/reference/primitives) 참조표에, 검토형 적재 도구 네 개는 같은 문서의 [검토형 적재 연산](/reference/primitives#검토형-적재-연산-4개) 절에 빠짐없이 정리돼 있습니다.

봉투 말고 하나 더 다른 점이 있습니다. namespace 를 넘기는 방식입니다. MCP 호출에는 HTTP 헤더가 없으므로 조회 도구 여섯 개 모두 `namespace_id` 를 도구 인자로 받습니다(미지정 시 `default`). REST 참조표에서 `get_schema` 와 `get_entity` 에는 이 필드가 안 보이는데, REST 가 그 값을 인증 헤더로 받기 때문입니다. MCP 에서는 이 둘도 `namespace_id` 인자를 받습니다.

## 문서를 넣는 것도 같은 연결로

적재 도구 네 개가 같은 MCP 연결에 올라와 있으므로, 에이전트는 질의만 하는 게 아니라 문서를 그래프에 넣는 일까지 여기서 합니다. 순서는 `ingest_plan`(계획) → `ingest_preview`(미리 보기) → 질문이 있으면 `ingest_resolve`(질문 해소) → `ingest_commit`(확정)입니다. 계획과 미리 보기는 그래프에 아무것도 쓰지 않고, 사람이 무엇이 바뀌는지 확인한 뒤에야 확정 단계에서 실제로 반영됩니다. 각 단계가 받는 값과 돌려주는 값, 검토 흐름의 자세한 설명은 [문서를 그래프에 넣기](/guide/ingest)에 있습니다. 문서를 넣어 그래프를 채운 뒤, 같은 연결에서 아래 조회 도구로 곧장 질의하면 됩니다.

## 어느 도구를 먼저 부를까

질문의 모양에 따라 시작 도구가 갈립니다. 아래는 흔한 질문 유형과 그때 먼저 부를 도구, 이어 붙일 도구를 정리한 표입니다.

| 알고 싶은 것 | 먼저 | 이어서 |
| --- | --- | --- |
| 키워드밖에 없어 출발점부터 찾아야 할 때 | `find_entities` | 얻은 ID 를 아래 도구들에 넘김 |
| 한 개념의 이웃을 살필 때 | `get_neighbors` | 이웃 노드로 다시 `get_neighbors` |
| 두 개념이 실제로 이어지는지 확인할 때 | `find_path` | `hub_score` 로 경로 신뢰도 판단 |
| 여러 출발점을 한 번에 펼칠 때 | `get_subgraph` | 합쳐진 조각에서 관계 읽기 |
| 그래프에 뭐가 들었는지부터 볼 때 | `get_schema` | `find_entities` 로 출발점 찾기 |

거의 모든 흐름이 `find_entities` 에서 출발합니다. 사용자가 아는 건 보통 "환불 규정" 같은 말이지 노드의 ID 가 아니기 때문입니다. 노드를 ID 로 가리키는 나머지 도구를 쓰려면, 먼저 키워드를 ID 로 바꿔야 합니다. 그 첫 변환이 `find_entities` 의 몫입니다. 처음 보는 그래프라면 `get_schema` 로 어떤 타입이 들었는지부터 보고 키워드를 고르는 편이 낫습니다.

## 에이전트가 한 질문을 푸는 흐름

도구 하나로는 답이 잘 안 나옵니다. 쓸모는 여럿을 엮을 때 나옵니다. "이 프로모션에 어떤 환불 규정이 걸리나" 라는 질문으로, 에이전트가 도구를 어떻게 이어 부르는지 따라가 봅니다.

먼저 **출발점을 잡습니다.** 에이전트는 질문에서 핵심 낱말을 뽑아 `find_entities` 에 `{"keywords": ["여름 프로모션", "환불"]}` 처럼 넘깁니다. 돌아온 `matches` 에서 가장 잘 맞은 노드의 `id` 를 꺼내면, 이제 프로모션 노드와 환불 규정 노드의 ULID(26자리 식별자)를 손에 쥡니다. 여기서 결과가 비어 있다면 키워드가 그래프의 표현과 어긋난 것이니, 낱말을 바꿔 다시 부르거나 `get_schema` 로 실제 타입을 보고 고쳐 잡습니다.

다음으로 **관계를 따라갑니다.** 두 노드가 정말 이어지는지 궁금하다면 `find_path` 에 두 ID 를 넣어 경로가 있는지, 몇 단계인지 봅니다. 프로모션 하나에 걸린 규정을 넓게 훑고 싶다면 `get_neighbors` 로 프로모션 노드의 이웃을 한두 단계 펼쳐, 어떤 규정과 어떤 관계로 이어지는지 봅니다. 돌아온 `edges` 의 `from` 과 `to` 를 읽으면 어느 규정이 이 프로모션에 직접 걸리는지 드러납니다.

그리고 **응답을 읽어 판단합니다.** 에이전트는 돌아온 노드와 관계를 근거로 삼아, 지금까지 모은 조각이 질문에 답하기에 충분한지 가늠합니다. 규정 노드의 이름과 속성, 그 규정이 프로모션에 어떤 관계로 닿는지를 보고, 필요하면 규정 노드를 다시 `get_neighbors` 로 펼쳐 조건 하나를 더 캡니다. 충분하다 싶으면 그제야 모은 조각을 엮어 사람이 읽을 답을 만듭니다.

언제 멈출지도 정해 둬야 합니다. 세 가지 신호로 판단합니다. 조회가 **빈 결과**를 주면 그 갈래는 막힌 것이니 다른 출발점이나 키워드로 틀거나 탐색을 접습니다. 모은 조각이 질문에 답하기 **충분한 근거**가 되면 더 부르지 않고 답을 만듭니다. 그럴싸한 근거가 안 모여도 **호출 예산**(정해 둔 최대 호출 횟수)을 다 쓰면 멈추고, 가진 것으로 답하거나 모른다고 솔직히 말합니다. 이 판단은 모두 부르는 쪽 에이전트의 몫입니다. Arche 는 매 호출에 작은 사실 조각만 돌려줄 뿐, 언제 멈추고 어떻게 엮을지는 정해 주지 않습니다.

## hub_score 로 경로 고르기

`find_path` 가 경로를 여럿 돌려줄 때, 어느 경로를 근거로 삼을지는 에이전트가 골라야 합니다. 이때 각 경로에 딸려 오는 `hub_score` 가 길잡이입니다.

두 점이 이어졌다는 사실과 그 연결이 의미 있다는 사실은 다릅니다. 수많은 다른 점과 얽힌 노드(이하 과다 연결 노드)를 다리로 삼은 경로는 "닿긴 닿지만 의미가 약한" 연결일 때가 많습니다. `hub_score` 는 한 경로가 그런 과다 연결 노드를 얼마나 거쳐 가는지를 한 숫자로 알려 줍니다.

읽는 법은 상대적입니다. 정해진 합격선 같은 건 없습니다.

- **값이 낮을수록 더 구체적인 경로**입니다. 경쟁하는 경로가 여럿이면 `hub_score` 가 낮은 쪽을 먼저 근거로 삼으세요.
- **`hub_score` 가 0 이면 가장 단단한 연결**입니다. 두 점이 한 단계로 바로 이어졌거나, 거쳐 간 중간 노드가 모두 연결이 적은 고유한 점이라는 뜻입니다.
- **값이 클수록 의심하세요.** 아무 데나 연결된 과다 연결 노드를 다리로 삼았다는 신호입니다. 이 경로로만 닿는 결론은 강한 근거로 삼기 전에, 더 구체적인 다른 연결이 있는지 한 번 더 확인하는 편이 안전합니다.

값이 높다고 그 경로를 버릴 필요는 없습니다. 때로는 그것이 유일한 단서니까요. `find_path` 는 길이가 같은 경로들 사이에서 `hub_score` 가 낮은 것을 먼저 돌려주니, 앞에 오는 경로일수록 대체로 더 구체적입니다. 점수가 실제로 어떻게 계산되는지, 왜 낮은 값이 더 믿을 만한지는 [경로 품질과 hub_score](/concepts/path-quality)에서 측정값과 함께 다룹니다.
