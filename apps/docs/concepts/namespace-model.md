# namespace 격리 모델

한 그래프 DB 를 여러 팀이나 프로젝트가 같이 쓰는 상황을 생각해 봅시다. 그냥 두면 A 팀 문서에서 뽑은 노드가 B 팀 검색에 섞여 나오고, 같은 회사 이름이 두 팀 문서에 따로 등장했다가 하나로 잘못 합쳐지기도 합니다. namespace 는 이 섞임을 막는 칸막이입니다. 그래프 DB 는 하나만 띄워 두고, 그 안의 데이터와 질의를 각자의 칸 안에 가둬 서로 새어 나가지 않게 합니다.

실제 호출 방법은 [팀별 지식 격리](/guide/namespace) 가이드에 정리돼 있습니다. 이 글은 그 칸막이가 데이터 위에서 어떻게 표현되고 왜 이렇게 설계됐는지를 한 겹 더 들어가 다룹니다. 운영 모델을 정한 근거는 [ADR-0015](https://github.com/Jungho-Cheon/arche/blob/main/docs/adr/0015-shared-kb-operating-model.md)에 있습니다.

## 왜 칸을 단단히 나누나

칸을 나누는 방법으로 처음 떠오르는 건 팀마다 그래프 DB 를 따로 띄우는 것입니다. 그런데 그러면 DB 마다 백업과 모니터링, 업그레이드를 따로 돌봐야 해서 운영 무게가 빠르게 불어납니다. 게다가 한 사람이 회사 A 와 회사 B 를 함께 다니며 양쪽 지식을 한곳에 모으고 싶을 때, DB 가 갈라져 있으면 둘을 잇는 일이 또 별도 작업이 됩니다.

그래서 Arche 는 다른 길을 택했습니다. 그래프 DB 는 하나만 두고, 모든 노드에 "이 노드는 어느 칸 소속인가"를 적은 꼬리표를 붙입니다. 운영은 단일 인프라라 가볍고, 칸은 논리적 경계라 나중에 칸끼리 일부만 잇는 길을 열어 둘 여지도 남습니다.

## 칸은 모든 노드에 붙는 속성이다

핵심은 단순합니다. 칸은 별도의 저장소가 아니라 노드마다 들고 다니는 속성입니다. 그래프에 적재되는 엔티티에는 `namespace_id` 라는 필드가 있고, 그 값이 이 노드가 어느 칸에 속하는지를 정합니다. 엔티티뿐 아니라 문서 토막과 관계에도 같은 칸 꼬리표가 붙습니다. 관계는 양 끝 노드가 같은 칸일 때 그 칸 값을 물려받습니다.

이렇게 칸을 노드 속성으로 두면 격리가 자연스럽게 따라옵니다. 모든 조회에 "이 칸 것만"이라는 조건을 끼우면 다른 칸 노드는 검색 결과에서 통째로 빠지기 때문입니다. 칸을 가르려고 데이터를 물리적으로 떼어 놓을 필요가 없습니다.

## 쓰기와 합치기와 읽기 모두 칸 안으로

칸막이는 데이터가 드나드는 길목 전체에 걸립니다. 한 군데라도 새면 격리가 깨지므로, 세 길목 모두에 같은 칸 조건을 끼웁니다.

**쓰기(적재).** 문서에서 뽑은 노드와 관계는 그 요청이 속한 칸에 기록됩니다. `work-a` 칸으로 적재하면 거기서 만들어진 모든 점과 선이 `work-a` 꼬리표를 답니다.

**같은 대상 합치기.** 적재할 때 새 노드가 기존 노드와 같은 실체인지 따져 하나로 합치는 단계가 있습니다(이 합치기가 문서를 건너뛰는 사슬을 잇는 일을 합니다. [왜 그래프인가](/concepts/why-graph) 참고). 이 비교를 같은 칸 안에서만 합니다. 그래서 `work-a` 의 "John"과 `work-b` 의 "John"은 이름이 같아도 별개 노드로 남습니다. 동명이인이 멋대로 한 사람으로 뭉치지 않습니다.

**읽기(모든 조회).** 키워드 검색, 이웃 펼치기, 경로 찾기, 부분 그래프가 전부 그 칸 안으로 범위가 좁혀집니다. ID 를 직접 찍어 노드 하나를 가져오는 조회도 마찬가지입니다. 다른 칸에 있는 노드의 ID 로 부르면 그 노드가 실제로 있더라도 없는 것처럼 응답합니다. ID 를 이것저것 찍어 보며 옆 칸을 엿보는 우회로까지 막으려는 동작입니다.

## `default` — 칸을 안 나눈 경우의 기본 칸

칸을 따로 지정하지 않은 요청은 모두 `default` 라는 칸으로 갑니다. 그래프에 적재되는 엔티티의 `namespace_id` 는 기본값이 `default` 입니다.

이 기본값이 두 가지를 함께 해결합니다. 하나는 칸을 나눌 생각이 없는 사용자입니다. 칸 개념을 몰라도 그냥 적재하고 질의하면 전부 `default` 안에서 일관되게 동작합니다. 다른 하나는 칸 개념이 들어오기 전에 이미 쌓여 있던 옛 노드입니다. 그런 노드에는 `namespace_id` 가 없는데, 값이 없으면 `default` 소속으로 간주합니다. 옛 데이터를 일일이 다시 손대 칸 값을 채워 넣지 않아도 자연스럽게 한 칸에 묶입니다.

## 칸끼리 잇기는 아직 열려 있지 않다

지금 namespace 는 단단한 경계입니다. 한 질의가 여러 칸을 한꺼번에 보거나 한 칸의 일부만 다른 칸과 공유하는 일은 아직 안 됩니다. 칸을 넘나드는 질의가 필요하면 칸마다 따로 호출해 결과를 직접 합쳐야 합니다.

칸끼리 잇는 길은 일부러 닫아 두었습니다. ADR-0015 는 앞으로 칸 사이를 명시적으로 열 수 있는 공유 모델을 그려 두었지만(한 칸이 다른 칸을 읽기만 하게 하거나, 양방향으로 트거나, 일부 노드를 복제하는 식), 이는 어디까지나 사용자가 직접 켜는 옵션으로 설계됐고 아직 만들어지지 않았습니다. 공유를 켠 적 없다면 칸 사이에는 어떤 연결도 자동으로 생기지 않습니다.

이렇게 기본을 격리로 두는 데는 분명한 이유가 있습니다. 사내 공유 지식 베이스에서 칸이 의도치 않게 트이면 한 팀 정보가 다른 팀으로 새는 사고가 됩니다. 그래서 합치기 한 단계까지 칸 안에 가두고, 칸을 넘는 연결은 사람이 분명히 의도를 밝혔을 때만 생기게 했습니다. 편의보다 새지 않음을 먼저 둔 선택입니다.

::: tip 정리
- 칸은 별도 DB 가 아니라 모든 노드가 들고 다니는 `namespace_id` 속성입니다.
- 쓰기, 같은 대상 합치기, 읽기 세 길목 모두 그 칸 안으로 범위가 좁혀집니다.
- 칸을 지정하지 않은 요청과 칸 개념 이전의 옛 노드는 `default` 칸에 묶입니다.
- 칸끼리 잇기는 사용자가 직접 켜는 옵션으로 설계됐을 뿐 아직 만들어지지 않았습니다.
:::
