# 잘못 합친 노드 떼어내기

서로 다른 둘이 한 노드로 뭉쳐 버렸을 때 다시 가르는 방법이에요. "여름 프로모션"과 "여름 정산"이 이름이 닮았다는 이유로 한 점이 됐다면 여기서 되돌려요.

```json
{
  "entity_id": "01J8XR4K9ZQ2N7M3VB0W4D6TYE",
  "new_name": "여름 정산",
  "move_source_paths": ["/docs/약관.md"]
}
```

계획 → 미리 보기 → 확정, 세 번을 부르면 끝나요. 적재와 같은 순서라 확정 전까지 그래프는 그대로예요.

## 왜 급한 일인가

흩어짐과 뭉침은 증상이 반대예요. 같은 대상이 여러 노드로 흩어지면 질문이 답을 **못 찾아요**. 반대로 다른 둘이 한 노드에 뭉치면 그 점을 지나는 경로가 전부 거짓이 되고, 답은 나오되 **틀린 답이 나와요**. 없는 답보다 그럴듯한 오답이 나빠요.

뭉친 노드는 눈에도 잘 안 띄어요. 별칭이 유난히 많거나, 한 점에 성격이 다른 관계가 잔뜩 붙어 있으면 의심해 보세요.

## 무엇을 기준으로 가르나

두 가지를 넘겨요. **떼어낸 노드의 이름**과 **무엇이 따라갈지**예요.

`move_source_paths` 는 어느 문서의 몫을 떼어낼지 고르는 값이에요. 이게 관계를 가르는 기준이기도 해요. 관계마다 어느 문서에서 나왔는지가 남아 있어서, 그 출처가 떼어내는 쪽에만 있으면 따라가고 남는 쪽에만 있으면 남아요.

`move_aliases` 는 별칭을 나누는 값이에요. `new_name` 이 원래 노드의 별칭이었다면 따로 적지 않아도 함께 따라가요. 남겨 두면 옛 노드가 계속 그 이름으로 잡혀서 가른 의미가 없거든요.

둘 중 적어도 하나는 있어야 해요.

## 갈리지 않는 관계

출처가 양쪽에 걸쳐 있거나 아예 없는 관계는 자동으로 못 정해요. 이런 건 미리 보기의 `questions` 에 올라오고, **하나라도 남아 있으면 확정이 거부돼요.**

```json
{
  "relation_id": "01J8XR7P4QRS5T7U6VW7X8Y9ZA",
  "type": "APPLIES_TO",
  "other_name": "환불 정책",
  "source_paths": ["/docs/계약.md", "/docs/약관.md"],
  "decision": "ask",
  "reason": "출처가 양쪽에 걸침"
}
```

답을 정했으면 `relation_decisions` 에 담아 **계획부터 다시** 부르세요.

```json
{
  "entity_id": "01J8XR4K9ZQ2N7M3VB0W4D6TYE",
  "new_name": "여름 정산",
  "move_source_paths": ["/docs/약관.md"],
  "relation_decisions": { "01J8XR7P4QRS5T7U6VW7X8Y9ZA": "move" }
}
```

적재처럼 따로 질문 해소 단계를 두지 않은 건, 떼어내기는 계획에 AI 호출이 없어서 다시 세우는 게 거의 공짜이기 때문이에요.

`move_source_paths` 를 아예 비우면 관계를 가를 근거가 없어서 **전부** 질문으로 올라와요. 관계가 많은 노드라면 출처로 먼저 크게 나누는 편이 편해요.

## 떼어낸 노드는 어떤 모습인가

원래부터 있던 노드와 같아요. 자기 임베딩과 검색 색인을 갖고, 타입은 원래 노드에서 물려받고, 이름으로 바로 조회돼요. 설명도 원래 노드 것을 물려받는데, 산문을 기계적으로 가를 방법이 없어서예요. 새로 쓰고 싶으면 `new_description` 을 주세요.

물려받은 설명은 떼어낸 노드에는 안 맞을 수 있어요. "1975년 미국에서 설립된" 이 2020년 한국 조직에 그대로 붙는 식이에요. 미리 보기의 `description_inherited` 가 `true` 면 물려받았다는 뜻이니 확정 전에 한 번 읽어 보세요.

옮긴 관계도 마찬가지예요. 지우고 새로 만드는 게 아니라 출처와 만든 시각을 그대로 들고 옮겨 가요.

## 서로를 다시 빨아들이지 않아요

가른 뒤에 같은 문서를 또 넣으면 "여름 프로모션(별칭: 여름 정산)"이 다시 추출돼요. 예전 같으면 별칭이 도로 합쳐지면서 가른 결정이 조용히 무효가 됐을 거예요.

지금은 두 노드가 **서로의 이름을 거부해요.** 사람이 내린 결정이 유사도 임계값보다 세서, 임베딩이 아무리 가까워도 다시 붙지 않아요.

::: warning 원래 이름까지 막아 주지는 않아요
거부는 **가른 두 노드 사이에서만** 성립해요. 남은 노드는 자기 이름을 그대로 쓰니까, 새 문서가 떼어낸 쪽 내용을 **옛 이름으로** 부르면 그 내용은 남은 노드에 다시 붙어요. 뭉쳤던 그 경로가 다시 열리는 거예요.

애초에 뭉친 이유가 두 대상을 같은 이름으로 부르는 문서였다면 이 일이 실제로 일어나요. 가른 뒤 한동안은 [무엇이 들어갔는지](/ingest/quality) 확인하고, 필요하면 남은 쪽 이름도 헷갈리지 않게 바꾸세요.
:::

## 막히는 자리

**`그 이름의 노드가 이미 있습니다`** — 떼어내려는 이름의 노드가 그 타입에 이미 있어요. 새로 만들 게 아니라 그쪽으로 옮기는 게 맞는지 먼저 확인하세요.

**`출처를 전부 옮기면 원래 노드가 빈 껍데기로 남습니다`** — 모든 출처를 떼어내는 쪽으로 보냈어요. 그건 가르는 게 아니라 이름을 바꾸는 일이에요.

**`아직 정하지 않은 관계가 있습니다`** — `questions` 가 남은 채로 확정했어요. 결정을 `relation_decisions` 에 담아 다시 계획하세요.

**`떼어낼 노드가 사라졌습니다`** — 계획을 세운 뒤 그래프가 바뀌었어요. 다시 계획하세요.

되돌리기는 없어요. 잘못 갈랐다면 같은 문서를 다시 적재해 채우거나, 그래프를 비우고 처음부터 넣으세요. 그래서 확정 전에 미리 보기를 꼭 읽어야 해요.
