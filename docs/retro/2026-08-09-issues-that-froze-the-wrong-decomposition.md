# 회고: 잘못 쪼갠 이슈가 잘못된 실행을 그대로 통과시켰을 때

**날짜** 2026-08-09
**계기** "모든 이슈를 수정하고 리팩터하라" 로 시작해 이슈 목록을 위에서부터 실행했다.
**결과** 만든 것을 두 번 걷어냈다. 이슈 9 건 중 3 건이 다른 작업에 흡수되거나 취소됐다.

이 회고는 이 저장소보다 넓게 쓰려고 쓴다. 이슈를 어떻게 쓰는가, 에이전트에게 무엇을
요구하는가에 관한 내용이라 다른 프로젝트에도 그대로 적용된다.

## 무슨 일이 있었나

이슈 9 건이 열려 있었다. 각각 배경, 할 일, 완료 조건을 갖춘 잘 쓰인 이슈였다. 그대로
실행했다.

- #170 "임베디드에도 탐지를 구현한다. 표면을 하나 연다" → 구현했다.
- #171 "타입별 노드를 전부 나열하는 수단을 둔다" → 새 도구 `list_entities` 를 만들었다.
- #172 "가른 노드에 모호 표시를 남겨 사람에게 묻는다" → 질문 종류를 새로 설계했다.

셋 다 이슈에 적힌 대로였다. 셋 다 틀렸다.

`list_entities` 는 만들었다가 통째로 지웠다. #172 의 질문 장치는 설계 단계에서 접었다.
#163 은 만들지 않기로 하고 닫았다. #170 은 별도 작업이 아니라 #171 의 일부였다.

## 왜 그렇게 됐나

### 이슈가 분해 방식을 고정한다

#170, #171, #172, #159 는 네 건의 결함이 아니었다. **하나의 빠진 능력이었다.** 노드를
가르는 도구는 있는데 가를 노드를 찾는 방법도, 지우는 방법도 없었다. 넷은 그 하나가
드러난 네 가지 증상이었다.

그런데 이슈를 넷으로 쪼개 적는 순간 그 분해가 사실처럼 굳었다. 나도, 이슈를 쓴 사람도
공통 원인을 다시 보지 않았다. 각각을 성실히 실행할수록 서로 안 맞는 도구가 늘었다.

**이슈에 세부를 더한다고 나아지지 않는다.** 이 이슈들은 이미 자세했다. 분해가 틀린
상태에서 자세하면 자세하게 틀린 결과가 나온다.

### 적어 둔 전제는 아무도 다시 확인하지 않는다

세 이슈의 전제를 실제로 재 봤더니 셋 다 어긋나 있었다.

| 이슈가 주장한 것 | 실제 |
|---|---|
| `get_schema` 로는 타입별 개수를 알 수 없다 | 개수는 정확하다. 잘리는 건 예시뿐이다 |
| 이름이 겹치는 노드가 19 쌍 있다 | 지금은 0 이다. 앞선 수정이 이미 막고 있었다 |
| 가운뎃점이 170 건 남아 있다 | 405 건이었다 |

두 번째가 특히 컸다. 진단 도구를 만들 이유의 절반이 이미 사라진 상태였는데, 이슈에
적혀 있다는 이유로 그대로 만들고 있었다. 실제 자료를 재 보고서야 알았다.

### 목표를 주면 목록을 최대화하고, 기준을 주면 표면을 최소화한다

"모든 이슈를 수정하라" 는 완수를 최대화하게 만든다. 도구를 늘리는 쪽으로 간다.

작업 중간에 이 한 문장을 받았다.

> Arche 는 에이전트가 그래프 지식 베이스를 관리하는 데 필요한 것을 제공한다. 이 기준으로
> 코드베이스에 포함할지 말지를 결정한다.

그 뒤로 작업이 접혔다. 이슈 8 건이 5 건이 되고, 새 도구 둘이 하나가 되고, #172 의 질문
장치가 필드 하나가 됐다. **같은 노력이 반대 방향으로 갔다.**

### 잘못된 자리에서 고치면 끝없이 늘어난다

읽기 도구가 문제를 보고하게 만들고 있었다. 그때 이 지적을 받았다.

> 읽기 동작에서 지금 데이터만 고려하지 말고, 애초에 쓰기 단계에서 해결할 수 있는
> 문제인지 고민해라.

실제 그래프를 재 보니 이름 중복도 잘못된 병합도 0 이었다. 쓰기 쪽 수정이 이미 막고 있던
것이다. 남은 문제(관계가 하나도 없는 노드 8 건)는 계획 단계에서 계산할 수 있는데 아무도
알려 주지 않아서 통과한 것이었다.

읽기에서 고치면 자료 형식마다 대응이 늘어난다. 쓰기에서 고치면 형식과 무관하게 한 번
끝난다.

### 소비자가 스스로 할 수 있는 일은 만들지 않는다

"에이전트가 판단한다면 이 코드가 무의미해지는가" 라는 질문이 바로 쓰이는 판정 기준이
됐다.

**호출부가 이미 받은 응답으로 알아낼 수 있는가?** 그렇다면 만들지 않는다.

이 기준으로 방금 쓴 경고 하나를 지웠다. "관계가 하나도 없는 새 노드" 를 알려 주려 했는데,
미리 보기에 새 노드 목록과 관계 목록이 다 있으니 호출부가 차집합으로 구할 수 있었다.
반면 "버려진 관계" 는 응답 어디에도 없어서 남겼다.

같은 기준을 #172 에 적용하니 설계가 통째로 줄었다. 문제는 판단 규칙이 없는 게 아니라
**판단에 필요한 사실이 안 보이는 것** 이었다. 가른 흔적이 저장은 돼 있는데 어떤 읽기
응답에도 안 실려 있었다. 필드 하나를 노출하니 질문 장치도 해소 경로도 필요 없어졌다.

### 전제가 바뀌면 고치지 말고 다시 세운다

가장 많은 시간을 버린 방식이 이것이다. 지적이 올 때마다 그 자리만 고쳤다. 도구를
만들었다 지우고, 포트 시그니처를 도중에 바꾸고, 질의를 썼다 되돌렸다.

전제가 바뀌면 그 위에 쌓은 것을 손보는 게 아니라 다시 세워야 한다. 문서는 코드를 설명하는
파생물이라 나중에 고쳐도 되지만, 설계와 코드는 그렇지 않다.

## 다음부터 이렇게 한다

### 이슈를 쓸 때

- **증상과 작업 지시를 구분해서 적는다.** 무엇이 안 되는지는 쓰고, 무엇을 만들지는 쓰지
  않는다. "임베디드에도 구현한다" 대신 "임베디드에서는 뭉친 노드를 찾을 수 없다" 로.
- **이슈를 열 때 전제에 날짜를 붙인다.** "2026-08-09 기준 19 쌍" 이라고 적어 두면 나중에
  읽는 사람이 다시 재야 한다는 것을 안다.
- **연관된 이슈는 묶어서 열거나, 최소한 서로를 가리키게 한다.** 넷이 한 원인이면 그 사실을
  어딘가에 적어야 각자 실행되는 것을 막는다.

### 에이전트에게 요구할 때

**목표 대신 포함 기준을 준다.** 가장 효과가 컸다.

```
<제품>은 <소비자>가 <목적>을 이루는 데 필요한 것을 제공한다.
이 기준으로 이슈를 다시 평가하고, 통과하는 것만 해라.
```

**이슈 본문을 사양이 아니라 증상으로 읽게 한다.**

```
이 이슈들은 증상 목록이다. 공통 원인을 먼저 찾아라.
본문에 적힌 해결 방법은 무시해도 된다.
```

**전제를 재고 시작하게 한다.**

```
설계 전에 이슈의 전제가 지금도 참인지 실제 자료로 확인해라.
```

**설계 관문을 둔다.** 중간에 이걸 받은 뒤로 되돌리는 일이 멈췄다.

```
설계를 먼저 내라. 승인 전에는 코드를 쓰지 마라.
```

**고칠 자리를 지정한다.**

```
읽기에서 대응하지 말고 쓰기에서 막을 수 있는지 먼저 봐라.
```

### 코드를 볼 때

- **주석이 필요한 곳은 설계를 의심한다.** 설명해야 이해되는 코드는 일반적이지 않은 방법으로
  푼 것이다. 주석 수를 그 자리의 부채 점수로 써도 된다.
- **비어 있지 않은 응답 필드마다 묻는다.** 호출부가 이미 아는 것인가.

## 이번에 잘 된 것

전부 잘못된 건 아니었다. 두 가지는 제대로 작동했다.

**가드 테스트가 즉시 잡았다.** 새 도구를 등록하자마자 문서 동기화 테스트와 namespace
검사 누락 테스트가 깨졌다. 조용히 어긋나는 대신 소리를 냈다. 앞선 회고에서 만든 장치가
이번에 값을 했다.

**실제 자료를 재 본 것이 방향을 바꿨다.** 코드만 읽었으면 이름 중복이 이미 0 이라는 것을
몰랐을 것이다. 그 하나가 진단 중심 설계를 접게 만들었다.

## 한 문장

**이슈 목록은 이미 내려진 판단이다.** 실행하기 전에 그 판단이 지금도 맞는지 다시 봐야
한다. 그러지 않으면 잘 쓰인 이슈일수록 잘못된 실행을 자신 있게 통과시킨다.
