# 개요

Opentology는 LLM(거대 언어 모델, 예: ChatGPT·Claude)이나 AI 에이전트가 **특정 도메인에 대해 정확한 답을 내도록 돕는 그래프 기반 지식 베이스 도구**다. 일반 LLM은 상식은 잘 알지만, 회사 내부 규칙이나 도메인의 세세한 관계 — 예를 들어 "이 쿠폰이 이 상품에 적용되는 이유는 이 프로모션 규칙 때문이다" 같은 것 — 는 잘 모른다. 문서를 그대로 던져줘도 LLM이 그 안의 *관계*를 정확히 따라가기는 어렵다.

Opentology는 이 문제를 풀기 위해, 사람이 가진 비정형 문서·이미지를 받아 그 안의 **엔티티(=사물·개념)와 관계**를 뽑아내어 일종의 지식 지도(=그래프) 형태로 저장한다. 그리고 LLM이나 AI 에이전트가 이 지도를 보고 답을 만들 수 있도록 API와 MCP(Model Context Protocol, AI 에이전트가 외부 도구와 대화하는 표준 규약)라는 두 통로로 열어둔다.

## MVP가 검증하려는 가설 — Pareto 우월

> **같은 LLM 으로 측정했을 때, 그래프 노드 RAG + 탐색 (Opentology) 은**
>
> - **(가) 답변 정확도가 *full-context* 방식 (= 전체 코퍼스를 LLM 에 그대로 stuffing) 과 동등하면서 토큰·시간 비용이 훨씬 낮고,**
> - **(나) 비슷한 토큰·시간 비용 범위에서 *청크 벡터 RAG* 보다 답변 정확도가 더 높다.**

즉 *정확도-비용의 두 축* 에서 Opentology 가 두 대안에 대해 **Pareto 우월** (한 축에서 동등하면서 다른 축에서 우월) 한 위치를 차지함을 검증한다.

이 가설이 의도적으로 efficiency 에 초점을 두는 이유 — 2026 년 시점에 LLM 컨텍스트 윈도우가 1M-2M 토큰까지 커지면서 *"문서를 그냥 다 넣으면 LLM 이 알아서 답한다"* 가 옵션이 됐기 때문이다. 작은 코퍼스에서는 이 방식이 multi-hop 추론을 가장 단순하게 푼다. 그래서 Opentology 의 가치는 *"청크 RAG 보다 정확하다"* 가 아니라 ***"같은 답을 훨씬 적은 토큰·시간으로 낸다"*** 가 되어야 한다. *비율 차이* 는 LLM 이 더 싸지고 더 길어져도 약해지지 않는다.

## 이 MVP가 끝나면 무엇이 가능해지는가

본인 손에 다음 세 가지가 남는다.

1. 한 도메인(상거래 비즈니스 규칙)에 대한 **소스 문서 묶음**
2. 그 도메인의 *세 방식의 차이가 드러나도록* 의도된 **30 개 MCQ 질문 + 정답 + distractor 의도 메타데이터 + reference reasoning** (구체 형식은 ADR-0005 참조)
3. **결과 보고서 한 장** — 같은 질문에 대해 세 방식의 답변을 *정확도 + 질문당 토큰 + 질문당 응답 시간* 세 메트릭으로 비교 (3 컬럼 × 3 메트릭 = 9 칸 표). 세 방식:
   - (1) Full-context LLM (cost ceiling reference) — 전체 코퍼스를 LLM 컨텍스트에 stuffing
   - (2) 청크 벡터 RAG (대조)
   - (3) 그래프 노드 RAG + 탐색 (Opentology)

이 세 가지가 만족스러우면 다음 단계(FE, 인증, 채팅 등)로 넘어간다. 만족스럽지 않으면 MVP 단계에서 가설을 다시 짚는다.

# MVP 범위

## In scope (이번에 만든다)

1. **비정형 소스 입력** — `.txt`, `.md`, `.pdf`, 이미지. 사용자가 폴더 경로를 지정하면 그 폴더를 재귀적으로 크롤한다.
2. **멀티모달 LLM으로 엔티티/관계 추출** — 텍스트뿐 아니라 이미지에서도 정보를 뽑을 수 있는 LLM 사용.
3. **그래프 데이터베이스 적재** — 추출 결과를 저장. *같은 소스를 두 번 넣어도 같은 그래프가 나오도록* 결정적(idempotent)으로 동작.
4. **그래프 진입점 인덱스** — 각 엔티티 노드에 dense 임베딩을 두고, 어휘 매칭(BM25 류)과 함께 결합해 자연어 쿼리에서 진입점을 찾는다. *단, 벡터는 retrieval의 주재료가 아니라 그래프 진입점을 찾는 인덱스 역할에 한정한다.* 별도 벡터 DB 서비스는 두지 않고, 그래프 DB 가 내장 제공하는 벡터 인덱스를 사용한다.
5. **Graph Primitives API + MCP** — `find_entities` / `get_entity` / `get_neighbors` / `find_path` / `get_subgraph` / `get_schema` 같은 *원자적 그래프 작업* 만 REST 와 MCP 양쪽으로 노출. *자연어 처리는 Opentology 의 책임이 아님* — caller (에이전트 또는 벤치마크 하니스) 가 자체 LLM 으로 anchor 키워드를 추출한 뒤 primitives 를 호출. 표면 결정의 근거와 primitive 명세는 [ADR-0006](../adr/0006-mcp-rest-primitives-surface.md).
6. **검증 산출물** — 위 "이 MVP가 끝나면 무엇이 가능해지는가"에 적은 세 가지.

## Out of scope (이번에는 안 만든다 — post-MVP로 이월)

"영원히 안 만든다"는 뜻이 아니라 *이번 검증이 끝난 다음에 만든다*는 뜻이다. 핵심 가설 검증에 직접 기여하지 않는 항목을 의도적으로 미룬다.

- **웹 화면(FE) 전부** — 관리 UI, 검색 UI 모두 없음. 그래프 데이터 확인이 필요하면 그래프 DB 벤더가 기본 제공하는 GUI(예: Neo4j Browser)를 그대로 쓴다.
- **인증·접근제어·멀티 테넌트** — MVP는 단일 환경에서 본인이 운영하는 것으로 가정한다. 여러 사용자 분리, 권한 관리, 로그인은 post-MVP 1순위 복귀 항목이다.
- **채팅 / 멀티턴 세션** — 단발 쿼리만. 이전 답을 이어가는 멀티턴은 채팅 기능과 함께 다음 단계에서.
- **다국어 처리** — 검증 도메인의 단일 언어로 시작.
- **엔티티/관계 변경 이력 audit** — 누가 언제 뭘 바꿨는지의 audit 로그는 없음. 단, "같은 소스를 두 번 넣으면 같은 그래프"라는 idempotent 동작은 유지한다.

# 기능 상세

## 소스 입력

1. 사용자가 디렉토리 경로를 지정하면, 해당 폴더를 재귀적으로 탐색해 지원 포맷(`.txt`, `.md`, `.pdf`, 이미지) 파일을 모두 수집한다.
2. 수집된 소스는 멀티모달 LLM에 전달되어 엔티티와 관계로 변환된다.
   - 소스 크기가 LLM 컨텍스트 윈도우를 초과할 때만 청크로 분할한다.
   - 분할 시에도 *하나의 소스 내 관계 정보가 유실되지 않는 것*을 우선 원칙으로 한다.
   - 분할이 오히려 비효율적인 경우 채택하지 않는다.
3. 결과물은 (엔티티, 관계) 튜플로 출력된다.
   - **엔티티**: 이름과 속성을 가진다.
   - **관계**: 두 엔티티를 연결한다.

## 그래프 적재

1. 추출된 엔티티와 관계를 그래프 데이터베이스에 저장한다.
2. **엔티티 동일성 판단** — 새로 들어온 엔티티가 그래프에 이미 있는지 판단할 수 있어야 한다. 구체적인 알고리즘(이름 매칭, 임베딩 유사도, LLM judge 등)은 구현 설계 단계에서 결정한다.
3. **신규 → 저장 / 기존 → 속성 병합** — 이미 있는 엔티티면 속성을 추가·갱신한다.
4. **결정적 동작 (idempotent)** — 같은 소스를 두 번 넣어도 같은 그래프가 나와야 한다. 검증의 *재현성*을 위해 필수.

## 그래프 진입점 매칭

진입점 선정은 *caller 와 Opentology 로 책임이 분리된다* (자세한 근거는 ADR-0006).

1. **caller 의 anchor 추출** — caller (에이전트·하니스) 가 자체 LLM 으로 질문에서 anchor 키워드 (정규명 + 별칭) 를 추출한다. *Opentology 의 컴포넌트가 아님.*
2. **Opentology 의 하이브리드 매칭** (`find_entities(keywords)` primitive 안에서):
   - **어휘 매칭** — 엔티티 이름·별칭에 대한 정확/fuzzy 문자열 매칭 (BM25 류).
   - **dense 벡터 유사도** — caller 가 보낸 키워드를 server-side 에서 임베딩한 뒤, 노드 임베딩과의 ANN 유사도.
3. dense 임베딩은 그래프 DB 가 내장 제공하는 벡터 인덱스에 저장한다. 별도의 벡터 DB 서비스는 두지 않는다.
4. 노드 단위 임베딩 모델은 검증 단계에서 *청크 벡터 RAG 베이스라인과 동일한 임베딩 모델* 을 사용한다. 비교의 통제 변수.
5. 두 신호의 결합 (RRF 등) 결과 top-k 가 `find_entities` 의 응답.

## 쿼리 (Graph Primitives)

클라이언트 (LLM 에이전트 또는 벤치마크 하니스) 가 Opentology 의 REST 또는 MCP primitives 를 조합해 필요한 정보를 모은다. 일반적인 흐름:

```
[자연어 질문]
  → caller LLM 으로 anchor 추출
  → find_entities(keywords)         → 진입점 노드 N 개
  → get_neighbors / find_path / get_subgraph  → 결과 서브그래프
  → caller LLM 으로 최종 답변 생성
  → [자연어 답변]
```

모든 primitive 응답은 다음 공통 메타데이터를 포함한다.

- 노드/엣지 정보 (id, name, type, attributes)
- 원본 소스 (파일 경로, 추출 위치)
- 추가일·수정일 timestamp

**단발 / Stateless** — 각 primitive 호출은 독립적이다. Opentology 는 세션을 유지하지 않는다. caller 가 여러 호출을 조합해도 *컨텍스트는 caller 쪽* . 멀티턴 채팅은 MVP 에서 제공하지 않는다.

# 컴포넌트

1. **API 서버 (FastAPI)** — 핵심 비즈니스 로직 + REST API + MCP 어댑터. graph primitives 노출 (ADR-0006).
2. **멀티모달 LLM (외부 서비스, *ingest 시점만*)** — 입력 소스에서 엔티티·관계 추출에만 사용. *쿼리 시점에는 호출하지 않음* — 자연어 처리 (anchor 추출, 답변 생성) 는 caller (에이전트·하니스) 의 책임 (ADR-0006). 모델 선택은 구현 단계 결정.
3. **임베딩 모델** — (a) ingest 시 엔티티 노드의 dense 임베딩 생성, (b) 쿼리 시 caller 가 보낸 키워드를 server-side 임베딩 (하이브리드 매칭용). 검증 단계에서 *청크 벡터 RAG 베이스라인과 동일 모델* 을 사용한다. 모델 선택은 구현 단계 결정.
4. **그래프 데이터베이스** — 엔티티·관계 저장 + 내장 벡터 인덱스 + 내장 풀텍스트 인덱스를 한 컴포넌트에서 모두 처리한다. *별도의 벡터 DB 서비스는 두지 않는다.* 벤더 선택은 구현 단계 결정 (단, 위 세 기능을 모두 내장 제공하는 벤더로 한정). 참고로 power user 의 ad-hoc Cypher 작업은 *Neo4j MCP* 를 같은 DB 에 부가로 attach 해 사용 가능 (Opentology MCP 와 공존, ADR-0006 D6).

# 검증 방식

## 검증 도메인

검증 도메인은 **상거래 비즈니스 규칙** — 상품·카테고리·프로모션·쿠폰·재고 같은 개념이 다중 hop 관계로 얽혀 있는 영역. 본인이 가장 잘 아는 도메인이므로 *정답 셋 작성 비용*이 최저이고, 차이를 만들 만한 관계 구조가 충분히 풍부하다.

## 소스 셋 구성 원칙

소스는 *세 방식의 답변 차이가 드러나도록* 의도적으로 구성한다.

- **다중 hop 관계** — 한 문서만으로는 답이 안 나오고 여러 엔티티를 따라가야 답이 나오는 구조 (예: 상품 → 카테고리 → 적용 가능 프로모션 → 쿠폰).
- **동의어·별칭** — 같은 개념이 여러 이름으로 등장하는 상황.
- **Cross-source 질문** — 답이 단일 문서에 모이지 않고 여러 문서를 결합해야 만들어지는 질문.

## Q&A 셋 — MCQ + 이유 서술 형식

30 개 질문은 **4-5 지선다 + "정보 부족" 옵션** 으로 구성한다. 각 distractor (오답 선택지) 에는 *어떤 실패 모드를 테스트하는지* 메타데이터를 붙인다 (예: `missed_category_hop`, `wrong_promotion_filter`, `retrieval_failure`). 본인은 각 질문에 *reference reasoning* (정답으로 가는 경로) 도 함께 작성한다. 형식 상세와 채점 절차는 [ADR-0005](../adr/0005-measurement-methodology-accuracy-tokens-latency.md) 를 따른다.

이 형식의 핵심 효용 두 가지 — (a) Correctness 채점이 자동화되어 judge 편향이 끼지 않고, (b) distractor 의 failure mode 추적으로 *"어디서 실패하는가"* 가 보고서에서 직접 보인다.

## 3-way 비교 절차

같은 30 개 MCQ 질문에 대해 세 컬럼이 만든 답변을 기록한다. 각 컬럼에서 *정확도 점수 (0-4, ADR-0005 D3)*, *질문당 토큰 합계*, *질문당 wall-clock 응답 시간* 세 메트릭을 측정한다.

1. **Full-context LLM (cost ceiling reference)** — 검증 도메인의 전체 코퍼스를 LLM 컨텍스트에 stuffing 한 뒤 질문. 정확도와 비용의 상한 기준점.
2. **청크 벡터 RAG (대조)** — 동일 소스 셋을 청크 단위로 분할하고 임베딩한 뒤, 질문에 대해 벡터 검색으로 관련 청크 top-k 를 LLM 에 컨텍스트로 제공.
3. **그래프 노드 RAG + 탐색 (Opentology)** — 동일 소스 셋을 Opentology 에 적재 (엔티티·관계 추출 + 노드 임베딩) 한 뒤, 질문에서 anchor 멘션을 LLM 으로 추출 → 진입점 노드 선정 → 그래프 traversal → 결과 서브그래프를 LLM 에 컨텍스트로 제공.

**Pareto 우월 검증**:
- **가설 (가) 통과** — (3) 의 정확도 ≥ (1) 의 정확도 **그리고** (3) 의 토큰·시간 ≪ (1) 의 토큰·시간
- **가설 (나) 통과** — (3) 의 정확도 > (2) 의 정확도 **그리고** (3) 의 토큰·시간이 (2) 와 비슷한 차수

**통제 변수**:
- 동일 LLM — 세 컬럼 모두 같은 답변 생성 모델
- 동일 임베딩 모델 — (2) 의 청크 임베딩과 (3) 의 노드 임베딩에 같은 모델 사용 (full-context 는 임베딩 미사용)
- N=3 회 반복 측정 (LLM API 변동성 흡수), 중간값 보고
- temperature = 0 (또는 최저값) 고정

## 종료 조건

MVP 종료 시점에 위 비교 결과를 **한 장의 보고서** (3 컬럼 × 3 메트릭 = 9 칸 표 + failure mode breakdown + 한 단락 해석) 로 정리한다. 보고서를 보고 본인이 "가설이 충분히 검증됐다" 고 판단하면 MVP 는 종료된다.
