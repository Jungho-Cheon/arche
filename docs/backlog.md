# 기능 추가 백로그

아직 ADR 이나 PRD 로 확정하지 않은 기능 후보를 모아 둔다. 항목마다 *배경 / 무엇을 할 것인가 / 완료 조건 / 열린 질문* 을 담고, 착수가 정해지면 GitHub Issue 나 spec 으로 옮긴다.

용어는 [용어집](../apps/docs/reference/glossary.md) 을 따른다. 자주 나오는 것만 짧게 풀면, **노드** 는 그래프의 점(회사, 정책 같은 하나의 대상), **관계** 는 노드를 잇는 선, **적재** 는 문서에서 노드와 관계를 뽑아 그래프에 넣는 일, **검토형 적재** 는 계획 → 미리 보기 → 질문 해소 → 확정 순서로 사람이 확인한 뒤에야 그래프에 쓰는 방식이다. **MCP (Model Context Protocol)** 는 AI 에이전트가 외부 도구를 정해진 방식으로 부르게 해 주는 표준 규약이다.

## 구현을 마친 항목

### B-1. 잘못 합친 노드를 떼어내는 연산 (2026-08-09)

동일성 해소가 틀려 서로 다른 둘이 한 노드에 뭉쳤을 때 두 노드로 가르는 연산이다. 별칭과 출처를 나눠 배정하고, 관계는 어느 문서에서 나왔는지를 따라 자동 배분하며, 갈리지 않는 관계만 사람에게 묻는다. 가른 결정은 노드에 남아 재적재가 둘을 다시 합치지 못한다.

열린 질문 넷은 이렇게 정했다.

- **재적재와의 화해** — 부정 결정을 노드에 붙였다 (`StoredEntity.blocked_aliases`). 별도 기록을 두지 않은 건 결정이 노드의 성질이지 별개 사실이 아니기 때문이다.
- **되돌리기의 되돌리기** — 두지 않았다. 잘못 갈랐으면 같은 문서를 다시 적재해 채우거나 처음부터 넣는다. 그래서 확정 전 미리 보기가 필수다.
- **범위** — 한 번에 둘로만 가른다. 셋 이상은 두 번 가르면 되고, 그 편이 미리 보기가 읽힌다.
- **B-2 와의 순서** — B-2 를 먼저 했다. REST 표면을 맞춰 둔 덕에 떼어내기도 MCP 와 REST 두 통로에 한 번에 올라갔다.

문서는 [잘못 합친 노드 떼어내기](../apps/docs/ingest/split.md), 설계 배경은 `apps/api/src/arche_api/domain/README.md` 의 "노드를 둘로 가르기".

### B-2. 검토형 적재 5개에 대응하는 REST 엔드포인트 (2026-08-09)

MCP 에만 있던 `ingest_plan` / `ingest_content` / `ingest_preview` / `ingest_resolve` / `ingest_commit` 을 `/ingest/*` 로 열었다. 스키마와 서비스 함수를 MCP 와 공유하고, 계획 보관소를 앱 수명 동안 하나만 두어 한 통로에서 세운 계획을 다른 통로에서 확정할 수 있다.

열린 질문 넷은 이렇게 정했다.

- **계획을 그래프에 남길 것인가** — 남기지 않았다. 확정 전에는 그래프에 아무것도 쓰지 않는다는 규약이 이 기능보다 무겁다. 대신 수명 제약을 문서에 명시했다.
- **계획의 만료** — 기본 3600초 뒤 버린다 (`ARCHE_API_PLAN_TTL_SECONDS`). 미리 보기나 질문 해소로 계획을 건드리면 시계가 다시 시작해, 검토 중인 계획이 사람 손에서 만료되지는 않는다.
- **경로 이름** — `/admin` 아래가 아니라 `/ingest/*` 로 두었다. 검토는 관리자 기능이 아니라 일상 작업이다.
- **파일 경로 문제** — `path` 가 서버가 보는 경로라는 점은 그대로 두되, REST 문서에서 본문을 직접 넘기는 `POST /ingest/content` 를 권장 경로로 안내한다.

문서는 [REST API](../apps/docs/reference/rest-api.md) 의 "검토형 적재 5개와 떼어내기 3개".
