# 기능 추가 백로그

아직 ADR 이나 PRD 로 확정하지 않은 기능 후보를 모아 둔다. 항목마다 *배경 / 무엇을 할 것인가 / 완료 조건 / 열린 질문* 을 담고, 착수가 정해지면 GitHub Issue 나 spec 으로 옮긴다.

용어는 [용어집](../apps/docs/reference/glossary.md) 을 따른다. 자주 나오는 것만 짧게 풀면, **노드** 는 그래프의 점(회사, 정책 같은 하나의 대상), **관계** 는 노드를 잇는 선, **적재** 는 문서에서 노드와 관계를 뽑아 그래프에 넣는 일, **검토형 적재** 는 계획 → 미리 보기 → 질문 해소 → 확정 순서로 사람이 확인한 뒤에야 그래프에 쓰는 방식이다. **MCP (Model Context Protocol)** 는 AI 에이전트가 외부 도구를 정해진 방식으로 부르게 해 주는 표준 규약이다.

---

## B-1. 잘못 합친 노드를 떼어내는 연산

### 배경

Arche 는 문서를 적재할 때 여러 문서에 흩어져 나온 같은 대상을 하나의 노드로 모은다 (동일성 해소). 이 합치기가 정확도의 레버다. 합쳐져 있어야 "A 계약 → B 부속 합의 → 기본 약관" 같은 문서를 건너뛰는 사슬이 이어지고, ADR-0016 에서 확인한 것처럼 그래프 정확도를 가르는 건 규모가 아니라 추출과 동일성의 완전성이다.

문제는 이 결정이 한 방향뿐이라는 데 있다. 지금은 **합친 것을 되돌리는 연산이 없다.** 서로 다른 대상을 하나로 잘못 뭉치면 복구 수단은 그래프 저장소를 통째로 비우고 처음부터 다시 적재하는 것뿐이다. 문서 열 개짜리 그래프라면 몰라도, 수백 개를 며칠에 걸쳐 쌓은 그래프에서는 사실상 되돌릴 수 없다.

그래서 지금 공개 문서는 사용자에게 *보수적으로 굴라* 고 안내한다. 검토형 적재가 "이 둘이 같은 대상입니까" 라고 물었을 때 "판단이 서지 않으면 따로 두는 쪽이 안전하다" 고 적혀 있다 ([문서를 그래프에 넣기](../apps/docs/ingest/index.md)). 이 안내 자체는 지금 상태에서 옳지만, 결과적으로 **흩어짐을 늘리는 방향으로 사용자를 민다.** 흩어진 노드는 문서를 건너뛰는 질문을 끊고, 그건 Arche 가 토막 검색보다 나은 유일한 이유를 깎는다.

즉 이 기능이 없어서 생기는 비용은 "가끔 잘못 합쳐서 불편하다" 가 아니라 "무서워서 안 합치고, 그래서 그래프가 덜 정확해진다" 다.

### 무엇을 할 것인가

한 노드에 모여 있는 것을 두 개 이상으로 가르는 연산을 만든다. 노드에는 여러 출처 (`source_refs`) 와 여러 별칭 (`aliases`) 이 붙어 있으므로, 가른다는 건 그것들을 새 노드와 원래 노드에 나눠 배정하는 일이다.

가장 어려운 부분은 **관계를 어느 쪽에 붙일지** 다. 잘못 합친 노드에는 두 대상의 관계가 뒤섞여 있다. 관계마다 어느 문서에서 나왔는지가 기록돼 있으므로 그 출처를 따라 자동 배분하고, 출처만으로 갈리지 않는 관계는 사람에게 묻는 방향이 현실적이다.

노출 방식은 기존 원칙을 따른다. 그래프를 바꾸는 길은 사람 확인을 거치는 검토형 적재뿐이고 (쓰기 도구는 MCP 에 올리지 않는다), 이 연산도 계획 → 미리 보기 → 확정 흐름에 얹는 게 일관적이다. 미리 보기에서 "새 노드에 이 별칭과 이 관계가 가고, 원래 노드에는 이게 남는다" 를 보여 준 뒤 확정받는다.

### 완료 조건

- 대상 노드와 가를 기준 (별칭 또는 출처) 을 주면 두 노드로 갈라지고, 각 노드가 자기 몫의 별칭과 출처를 갖는다.
- 관계가 출처를 따라 자동 배분되고, 갈리지 않는 관계는 사람 판단 항목으로 올라온다.
- 확정 전까지 그래프에 아무것도 쓰이지 않는다 (미리 보기 단계에서 취소 가능).
- 가른 뒤에도 같은 문서를 다시 적재했을 때 갈라 둔 결정이 유지된다. 다시 합쳐지면 이 연산은 무의미하다.
- 공개 문서 세 곳의 "떼어내는 연산은 아직 없습니다" 서술을 갱신한다: [Arche 소개](../apps/docs/about/intro.md), [문서를 그래프에 넣기](../apps/docs/ingest/index.md), [추출이 빈약할 때](../apps/docs/ingest/quality.md).

### 열린 질문

- **재적재와 어떻게 화해시킬 것인가.** 가른 결정을 어딘가에 남기지 않으면 다음 적재의 동일성 판단이 둘을 다시 합친다. "이 둘은 다른 대상" 이라는 부정 결정을 노드에 붙여 둘지, 별도 기록으로 둘지.
- **되돌리기의 되돌리기.** 잘못 갈랐을 때 다시 합치는 길이 필요한가. 합치기는 이미 재적재로 되니 별도 연산이 필요 없을 수도 있다.
- **범위.** 노드를 둘로 가르는 것만 할지, 세 개 이상으로 가르는 경우까지 받을지.
- **B-2 와의 순서.** 이 연산도 검토형 흐름을 쓰므로, REST 표면을 먼저 맞춰 두면 두 통로에 한 번에 올라간다.

## B-2. 검토형 적재 5개에 대응하는 REST 엔드포인트

### 배경

Arche 는 같은 기능을 두 통로로 내놓는 걸 원칙으로 한다. AI 에이전트가 쓰는 MCP 와, 에이전트 없이 코드에서 직접 부르는 REST API 다. **조회 도구 7개는 이 원칙을 지킨다.** 같은 이름과 같은 스키마로 양쪽에 올라온다.

적재만 어긋나 있다. 사람 확인을 거치는 검토형 적재 5개 (`ingest_plan`, `ingest_content`, `ingest_preview`, `ingest_resolve`, `ingest_commit`) 는 MCP 에만 있다. REST 로 문서를 넣는 유일한 길은 `POST /admin/ingest` 인데, 이건 검토 단계가 없어서 사람이 보기도 전에 그래프에 바로 쓴다.

이 비대칭이 만드는 결과가 셋이다.

첫째, **에이전트를 안 쓰는 통합에서는 검토를 낄 수 없다.** 사내 시스템이 Confluence 나 위키를 주기적으로 밀어 넣는 식의 사용에서, 무엇이 새로 생기고 무엇이 합쳐지는지 확인하고 반영하는 흐름을 REST 만으로는 못 만든다. 전부 받거나 전부 안 받거나다.

둘째, **OpenAPI 로 만든 클라이언트가 적재를 덮지 못한다.** `/openapi.json` 에서 언어별 클라이언트를 생성해도 검토형 적재는 스펙에 없어서 빠진다. 이 사실이 공개 문서에 예외 조항으로 적혀 있는데 ([REST 로 붙이기](../apps/docs/integrate/rest.md)), 예외 조항이 필요하다는 게 곧 표면이 덜 채워졌다는 뜻이다.

셋째, `ingest_content` (파일 경로 대신 텍스트를 바로 넘기는 도구) 가 MCP 에만 있다. 외부에서 읽어온 내용을 임시 파일 없이 넣는 길이 REST 에는 아예 없다.

구현 부담은 생각보다 작다. 다섯 도구의 실제 동작은 이미 `apps/api/src/arche_api/api/services.py` 의 `plan_ingest` / `plan_ingest_content` / `preview_plan` / `resolve_ingest` / `commit_plan` 에 있고, MCP 서버는 그걸 부르기만 한다. 요청과 응답 스키마도 `plan_schemas.py` 에 이미 정의돼 있다. **없는 건 라우터뿐이다.**

### 무엇을 할 것인가

다섯 개의 HTTP 엔드포인트를 추가하고, 기존 조회 엔드포인트와 같은 규약 (성공은 `data` 로 감싸고, 실패는 `error`, 루트와 `/v1` 양쪽에 올림, `Authorization` 헤더로 namespace 결정) 을 따르게 한다. 스키마는 MCP 와 같은 것을 쓴다 — 조회 7개가 그렇듯 한 곳에서 나와야 두 통로가 어긋나지 않는다.

진짜 설계 쟁점은 라우팅이 아니라 **계획을 어디에 두느냐** 다. 지금 `plan_id` → 계획 매핑은 `api/plan_registry.py` 의 프로세스 안 딕셔너리다. 앱이 사는 동안만 유지되고 재시작하면 사라진다. 이건 "한 사람이 자기 컴퓨터에서 stdio 로 쓴다" 는 가정에서 나온 트레이드오프이고 그 맥락에서는 타당하다.

REST 는 가정이 다르다. 계획을 세운 요청과 확정하는 요청이 다른 프로세스에 닿을 수 있고 (워커를 여럿 띄우면), 서버가 재시작되면 진행 중이던 검토가 통째로 날아간다. 사람이 미리 보기를 확인하는 데 걸리는 시간을 감안하면 이 창은 짧지 않다. 그래서 이 항목은 사실상 *계획의 수명을 어디까지 보장할 것인가* 를 정하는 일이다.

### 완료 조건

- 다섯 엔드포인트가 열리고, MCP 도구와 같은 요청/응답 스키마를 쓴다.
- `POST /admin/ingest` 와의 차이 (검토 있음 / 없음) 가 REST API 참조 문서에 명시된다.
- 계획 수명이 문서에 적힌 대로 동작한다. 프로세스 안에만 둘 거라면 "서버를 재시작하면 진행 중인 계획이 사라진다" 를 명시하고, 여러 워커에서 깨지지 않도록 배치 제약도 함께 적는다.
- 미리 보기를 거치지 않은 확정이 REST 에서도 `unprocessable` 로 거부된다. MCP 에만 있는 안전장치가 REST 에서 뚫리면 안 된다.
- OpenAPI 스펙에 다섯 엔드포인트가 올라오고, [REST 로 붙이기](../apps/docs/integrate/rest.md) 의 "검토형 적재 도구 5개는 MCP 에만 있어 스펙에 없습니다" 예외 조항과 [적재 도구 참조표](../apps/docs/ingest/tools.md) 의 같은 서술을 걷어낸다.

### 열린 질문

- **계획을 그래프 저장소에 남길 것인가.** 남기면 재시작과 다중 워커를 견디지만, 미확정 상태가 그래프에 들어간다. 확정 전에는 그래프에 아무것도 쓰지 않는다는 지금 규약과 어떻게 화해시킬지.
- **계획의 만료.** 확인 없이 방치된 계획을 언제 버릴지. 지금은 프로세스가 죽을 때까지 남는다.
- **경로 이름.** `/ingest/plan` 처럼 새 묶음으로 둘지, 기존 `/admin/ingest` 아래에 붙일지. 후자는 검토가 관리자 기능이라는 인상을 준다.
- **`ingest_plan` 의 파일 경로 문제.** `path` 는 서버가 보는 경로다. `POST /admin/ingest` 의 `directory_path` 가 이미 같은 이유로 자주 걸리는 자리인데, 파일 단위에서도 같은 혼동이 반복된다. REST 에서는 `ingest_content` 쪽을 권장 경로로 안내할지.
