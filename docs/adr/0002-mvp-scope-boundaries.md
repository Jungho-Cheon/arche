# ADR-0002: MVP 범위 경계 — 무엇을 의도적으로 미루는가

Status: accepted
Date: 2026-06-15

## TL;DR

MVP 의 검증 가설 (ADR-0001) 에 *직접 기여하지 않는* 항목 — 웹 화면 전부, 인증·접근제어·멀티테넌트, 채팅·멀티턴 세션, 다국어 처리, 엔티티/관계 변경 이력 audit — 을 *이번에는 만들지 않는다.* "영원히 안 만든다" 는 뜻이 아니라 *이번 검증이 끝난 다음에 만든다* 는 뜻이다. 각 항목에는 post-MVP 복귀 우선순위가 명시되어 있다.

## 이 ADR 을 읽는 이유

- MVP 범위에서 어떤 것이 *왜* 빠졌는지 확인하고 싶다면
- 본인이 MVP 에서 다루고 싶은 기능이 *out of scope* 인지 *in scope* 인지 빠르게 판단하고 싶다면
- post-MVP 에서 무엇부터 복귀할지 (= 다음 마일스톤의 후보) 가 궁금하다면

## 읽기 전 권장 배경

- [ADR-0001 — 프로젝트 정체성과 MVP 검증 가설](./0001-project-identity-and-mvp-validation-hypothesis.md) 이 *기여하지 않으면 빠진다* 의 *기여 기준* 을 설명한다.

## Context — 왜 이 결정이 필요했나

MVP 의 명시적 임무는 한 줄 가설 검증 (ADR-0001 D2) 이다. *그것 하나만* 검증한다. 그러나 PRD 작성 초안에는 운영 기능 (audit, 멀티턴 세션) 과 확장 기능 (다국어, 멀티 테넌트, FE 관리 UI) 이 섞여 있었다 — 가설 검증을 *지지* 하는 것처럼 보이지만 실제로는 *기여하지 않는* 항목들이다.

이 항목들이 MVP 에 들어오면 두 종류 비용이 발생한다.

1. **직접 구현 비용** — 코드·테스트·운영 부담.
2. **간접 인지 비용** — 가설 검증의 *통제 변수* 가 더 많아진다. 예를 들어 멀티 테넌트가 들어가면 *테넌트 격리 비용이 정확도에 영향을 주는가* 라는 부수 질문이 생기고, 보고서 한 장의 해석이 흐려진다.

게다가 메모리의 design principles 가드 ("형식주의 회피 · OSS+SaaS · 외부 의존 최소 · multi-tenant from day one" 등 7 개) 중 *multi-tenant from day one* 는 이 결정과 정면으로 충돌한다. 이 충돌은 의도적으로 *MVP 한정으로* 보류한다 — post-MVP 1 순위 복귀.

## Decision — 무엇을 결정했나

다음 항목을 *MVP 에서는 만들지 않는다* . 각 항목에 *왜 미루는가* 와 *언제 복귀하는가* 를 명시한다.

### D1. 웹 화면 (FE) 전부

- **왜 미루는가** — MVP 의 사용자는 *본인* (직접 운영자) 이고, 검증의 인터페이스는 *API 와 보고서 한 장* 이다. 관리 UI · 검색 UI 모두 가설 검증에 기여하지 않는다.
- **그래프 데이터를 보고 싶을 때는?** — 그래프 DB 벤더가 기본 제공하는 GUI (Neo4j Browser 등) 를 그대로 쓴다.
- **복귀 우선순위** — post-MVP 2 순위. 첫 외부 사용자가 본인 외에 생긴 시점부터.

### D2. 인증 · 접근제어 · 멀티 테넌트

- **왜 미루는가** — MVP 는 단일 환경에서 본인이 운영하는 것으로 가정한다. 여러 사용자 분리 / 권한 / 로그인은 *가설 검증에 직접 기여하지 않는다* . 또한 이 영역을 MVP 에 넣으면 보안 · 사용자 모델 결정이 *검증 가설보다 먼저* 고정되어 나중에 되돌리기 비싸진다.
- **메모리의 "multi-tenant from day one" 가드와 충돌하는데?** — 의도적으로 *MVP 한정으로* 보류한다. *post-MVP 1 순위 복귀 항목* 이다. archive 의 옛 ADR-0007, 0009, 0020 이 이 영역의 이전 결정을 담고 있어 복귀 시 그 자료를 *재검토* 한다 (복원하는 게 아니라 새 가설에 맞게 갱신).

### D3. 채팅 · 멀티턴 세션

- **왜 미루는가** — 가설 검증은 *단발 Q&A 3-way 비교* 다. 멀티턴은 검증과 다른 가설 ("멀티턴이 답변 품질을 올린다") 을 끌고 들어온다.
- **복귀 우선순위** — post-MVP 3 순위. 인증 · FE 가 들어온 다음에 의미가 있다.

### D4. 다국어 처리

- **왜 미루는가** — 검증 도메인 (상거래) 은 단일 언어로 충분하다. 다국어 자체가 가설의 차별점이 되지 않는다 — 그래프 KB 의 우월성은 *언어 수* 가 아니라 *관계 구조* 에서 나온다.
- **복귀 우선순위** — post-MVP 후순위. 첫 다국어 사용 사례가 생긴 시점부터.

### D5. 엔티티 / 관계 변경 이력 audit

- **왜 약화하는가** — "누가 언제 뭘 바꿨는지" 의 audit 로그는 *운영* 기능이다. MVP 검증에 필요한 건 *재현 가능성* — "같은 소스를 두 번 넣으면 같은 그래프" 라는 idempotent 동작 (ADR-0001 D6) — 으로 충분하다.
- **idempotent 는 유지** — audit 로그는 빠지지만 *결정성* 은 MVP 의 핵심 약속이다.
- **복귀 우선순위** — post-MVP 후순위. 다인 협업 + 검수 흐름이 들어올 때.

### D6. 운영자 평가 게이트 · CI 통합

- **왜 미루는가** — MVP 종료 조건은 *한 장의 보고서* 다 (ADR-0001 D7). 자동화된 평가 / 게이트 / CI 통합은 *검증 한 번* 에 필요하지 않다. archive 의 옛 ADR-0021, 0025 가 이 영역의 이전 결정을 담는다.
- **복귀 우선순위** — post-MVP 4 순위. 가설이 검증된 *다음* 에 *회귀 방지* 목적으로 들어온다.

## post-MVP 복귀 우선순위 요약

| 순위 | 영역 | 트리거 |
|---|---|---|
| 1 | 인증 · 접근제어 · 멀티 테넌트 | 가설 검증 성공 직후 |
| 2 | FE 관리 / 검색 UI | 첫 외부 사용자 생긴 시점 |
| 3 | 채팅 · 멀티턴 세션 | FE + 인증 안착 후 |
| 4 | 평가 게이트 · CI 통합 | 다인 협업 시작 시점 |
| 후순위 | 다국어, audit 로그 | 사용 사례 발생 시 |

이 순위는 *유동적이다* — MVP 종료 보고서의 결과에 따라 변경될 수 있다. 예를 들어 가설이 *부분적으로* 검증되면 1 순위가 *진입점 전략 보강* (ADR-0003 재검토) 으로 바뀔 수 있다.

## Considered Options

### 옵션 1 — 인증·멀티 테넌트만 MVP 에 포함, 나머지는 제외

거부. *의도적 가드와 정면 충돌하면서 가설 검증에는 기여하지 않는다* . 메모리의 "multi-tenant from day one" 가드를 *지키면서* 가설을 검증하는 비용이 *가드를 일시 보류하고 post-MVP 1 순위로 두는 비용* 보다 크다. 가드 자체가 *MVP 종료 직후 복귀* 라는 명시적 약속이 있으면 일시 보류는 정당하다.

만약 이걸 택했다면, 인증 / RBAC / 워크스페이스 모델 결정이 가설 검증보다 *먼저* 고정되어, 검증 결과가 부정적일 때 인증 모델까지 함께 갈아엎어야 했을 것이다.

### 옵션 2 — 모든 항목을 MVP 에 포함 (얇은 형태로)

거부. *얇은 형태로도 인지 비용이 폭발한다* . 각 항목이 "얇은 인증", "얇은 FE", "얇은 멀티턴" 으로 들어오면, 검증 보고서가 *각 변수의 영향* 을 풀어 해석해야 한다. 한 장의 보고서 (ADR-0001 D7) 가 다섯 장이 된다.

만약 이걸 택했다면, MVP 종료가 무기한 늦춰지고 *어떤 결정이 정확도에 기여했는지* 가 보고서에서 분리되지 않았을 것이다.

### 옵션 3 — 모든 항목을 post-MVP 로 두되 우선순위 없이 두기

거부. *후순위 없이 두면 MVP 종료 직후 무엇부터 할지 즉시 결정 비용이 든다* . 명시적 우선순위가 있으면 보고서를 본 직후 *다음 행동* 이 자동으로 결정된다.

만약 이걸 택했다면, MVP 종료 직후 "이제 뭐부터 하지?" 라는 메타 결정에 다시 시간을 썼을 것이다.

## Consequences

### 즉시 영향

- `docs/prd/1_mvp.md` 의 "Out of scope (post-MVP 로 이월)" 섹션이 이 ADR 과 일대일 대응한다.
- archive 의 옛 ADR-0007 (multi-tenant), 0009 (auth), 0014 (canvas), 0017 (notification), 0020 (RBAC), 0021 (eval gate), 0022 (main UI) 등은 *복귀 시 재검토 자료* 로 보존된다. 직접 복원하지 않는다.
- 메모리의 "multi-tenant from day one" 가드는 *MVP 한정 일시 보류* 라는 명시적 단서와 함께 유지된다 — 가드 자체를 폐기하는 게 아니다.

### 코드 작업 시 기억할 점

- MVP 코드 베이스에 *user / workspace / tenant* 모델을 *암시적으로* 끌어들이지 마라. post-MVP 복귀 시 충분히 의도적으로 도입할 수 있다.
- API 응답에 *현재 사용자* 같은 필드를 *임시로* 추가하지 마라 — 단일 환경 가정과 충돌하는 코드 흔적이 남는다.
- FE 가 없으므로 *API 의 OpenAPI 스키마* 가 사실상의 사용자 인터페이스다. 스키마 품질을 우선시한다.
- 변경 이력이 *audit 가 아닌 idempotent* 라는 약속을 잊지 마라. 노드에 `updated_at` 같은 *상태 추적* 필드는 둬도 되지만 *변경 로그* 컬렉션은 두지 않는다.
