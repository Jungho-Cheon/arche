# ADR-0001: 프로젝트 정체성과 MVP 검증 가설

Status: accepted
Date: 2026-06-15

## TL;DR

Opentology 는 LLM·AI 에이전트가 도메인의 *관계 정보* 를 *최소한의 토큰과 시간으로* 활용하도록 돕는 그래프 기반 지식 베이스 도구다. MVP 의 임무는 단 하나 — Opentology 가 **(a) full-context 방식 (코퍼스 전체 stuffing) 과 동등한 정확도를 훨씬 적은 토큰·시간으로 달성** 하고 **(b) 비슷한 토큰·시간 비용 범위에서 청크 벡터 RAG 보다 정확도가 높음** 을 *상거래 비즈니스 규칙* 도메인의 30 개 MCQ 질문 측정으로 확인하는 것이다 (Pareto 우월 가설). 결과 보고서 한 장이 MVP 의 종료 조건이다.

> **RAG (Retrieval-Augmented Generation)** — LLM 에게 답변을 시키기 전에 외부 지식 소스에서 관련 정보를 *먼저 검색* 해 컨텍스트로 같이 넣어주는 방식. "벡터 RAG" 는 그 검색을 *문서 청크의 임베딩 유사도* 로 하는 가장 흔한 형태다.

## 이 ADR 을 읽는 이유

- Opentology 가 *왜* 존재하는지, *무엇을* 검증하려고 만들어졌는지를 한 줄로 짚고 싶다면
- 다음 결정들 — MVP 범위(ADR-0002), 진입점 선정(ADR-0003), 벡터 인프라(ADR-0004) — 의 *맥락 가설* 을 이해하고 싶다면
- 본인의 도메인이 *상거래가 아닌데* Opentology 를 평가하려고 한다면 (이 ADR 의 검증 설계 원리를 본인 도메인에 옮길 때 무엇이 통제되어야 하는지)

## 읽기 전 권장 배경

이 ADR 은 다른 ADR 에 선행한다. 별도의 사전 읽기 권장 없음. 다만 `docs/prd/1_mvp.md` 가 이 ADR 의 자매 문서이며 *무엇을 만드는가* 의 더 자세한 사양을 담는다.

## Context — 왜 이 결정이 필요했나

LLM 은 일반 상식에는 강하지만 *도메인 내부의 관계* — 예를 들어 상거래에서 "이 쿠폰이 이 상품에 적용되는 이유는 이 프로모션 규칙과 카테고리 매핑 때문" — 같은 *다중 hop 추론* (= 한 노드에서 답이 나오지 않고 관계를 여러 번 따라가야 답이 만들어지는 추론) 에는 약하다.

2026 년 시점에 LLM 컨텍스트 윈도우가 1M-2M 토큰까지 커지면서 *"도메인 문서를 그냥 다 넣으면 LLM 이 알아서 hop 을 따라간다"* 가 현실적인 옵션이 됐다. 작은~중간 코퍼스에서는 이 방식이 multi-hop 추론을 가장 단순하게 푼다 — 청크 단위 retrieval 의 약점 (한 청크가 다른 청크에 의존하는 경우의 retrieval 실패, cross-source 질문에서의 retrieval 실패) 이 *전체를 다 보여주면* 자연히 사라진다.

그러나 "다 넣기" 는 세 가지 비용을 부과한다.

1. **토큰 비용** — 매 쿼리마다 전체 코퍼스를 LLM 에 보내면 비용이 코퍼스 크기에 선형 비례. 운영에서 누적되면 RAG/그래프 대비 *수십~수백 배* 차이.
2. **응답 시간** — 1M 컨텍스트 추론은 수십 초 이상. AI 에이전트의 turn 안에서 쓰기 어렵다.
3. **확장 한계** — 코퍼스가 컨텍스트 윈도우를 초과하는 순간 (사내 위키 전체, 연구 corpus, 다년치 운영 데이터 등) 옵션 자체가 사라진다. 그리고 *"Lost in the Middle"* 현상 — 컨텍스트가 커질수록 중간 위치 정보의 retrieval 정확도가 떨어지는 것 — 이 long-context 모델에서도 여전히 관찰된다.

Opentology 가 풀려는 문제는 ***"다 넣기" 가 줄 수 있는 답변 품질을, 훨씬 적은 토큰과 시간으로 달성하는 것*** 이다. 문서에서 엔티티·관계를 명시적 그래프로 추출해두면 — 질문 시점에 *필요한 부분만 추려서 LLM 에 넘길 수 있으면서*, 청크 단위 retrieval 이 놓치는 *문서 내·문서 간 연결* 을 *명시적 엣지로 보존* 하므로 추려진 결과가 답을 만들기에 충분하다.

이 가치 명제 — *"같은 답을 더 적은 토큰·시간으로"* — 는 LLM 컨텍스트가 더 커지거나 단가가 더 싸져도 약해지지 않는다. *비율 차이* 가 핵심이라서. 2024-2026 의 GraphRAG / LightRAG / HippoRAG / PathRAG 계열 연구가 공개 벤치에서 이 방향을 뒷받침해왔지만, *본인 도메인에서 본인 운영 비용으로* 같은 효과가 나오는지는 별개의 질문이다. MVP 의 임무는 *세상에 새 사실을 보태는 것* 이 아니라 *본인 도메인에서 같은 효과가 재현되는지 확인하는 것* 이다.

## Decision — 무엇을 결정했나

### D1. 프로젝트 정체성

Opentology 는 **LLM·AI 에이전트가 도메인 지식의 *관계* 를 활용해 답하도록 돕는, 그래프 기반 지식 베이스 도구다.** 사용 대상은 LLM 으로 문제를 풀려는 사람 누구든 — 본인의 개인 지식 베이스를 만드는 개발자, 사내 위키를 정돈하려는 도메인 담당자, 연구 문헌을 추적하는 연구자 등.

핵심 흐름은 세 단계다.

1. **소스 → 그래프 KB** — 비정형 문서·이미지를 받아 엔티티와 관계를 추출하고 그래프에 저장한다 (ingest 시점에만 LLM 사용).
2. **Graph Primitives 노출** — `find_entities` / `get_neighbors` / `find_path` / `get_subgraph` 등의 *원자적 그래프 작업* 을 REST 와 MCP (Model Context Protocol, AI 에이전트가 외부 도구와 대화하는 표준 규약) 양쪽으로 노출한다. *자연어 처리는 Opentology 의 책임이 아님* — caller (에이전트 / 하니스) 가 자체 LLM 으로 질문에서 anchor 를 추출한 뒤 primitives 를 호출. 표면 결정의 근거는 ADR-0006.
3. **재현성 보장** — 같은 소스를 두 번 넣어도 같은 그래프, 같은 키워드 호출에 같은 결과 (idempotent).

### D2. MVP 가 검증하려는 가설 — Pareto 우월

> **같은 LLM 으로 측정했을 때, 그래프 노드 RAG + 탐색은**
>
> - **(가) 답변 정확도가 full-context (전체 코퍼스 stuffing) 방식과 동등하면서 토큰·시간 비용이 훨씬 낮고,**
> - **(나) 비슷한 토큰·시간 비용 범위에서 청크 벡터 RAG 보다 답변 정확도가 더 높다.**
>
> 즉, *정확도-비용의 두 축* 에서 Opentology 는 두 대안에 대해 **Pareto 우월** (한 축에서 동등하면서 다른 축에서 우월) 한 위치를 차지한다.

이 가설은 *의도적으로 efficiency 에 초점을 둔다* . 단순 정확도 비교가 아니라 *정확도 / 토큰 / 지연 세 축의 동시 측정* 이 검증의 본체다. 이유는 long-context LLM 의 등장으로 *"그냥 다 넣으면 정확도는 나온다"* 가 현실에 들어왔기 때문 — 이 옵션이 *비용 측면에서 비현실적* 임을 증명하는 것이 가설의 절반이고, *그 비용을 줄이면서 정확도를 유지* 함을 증명하는 것이 가설의 나머지 절반이다.

도메인은 상거래 비즈니스 규칙으로 고정 (D4). 메트릭의 구체 산출 방법은 ADR-0005 (측정 방법론) 를 따른다.

### D3. 비교 실험 — 3-way 측정 (정확도 + 토큰 + 지연 3 메트릭)

같은 30 개 **MCQ 질문 + 이유 서술 강제** 에 대해 세 컬럼의 답변을 기록한다. 각 컬럼에서 *정확도 점수*, *질문당 토큰 합계*, *질문당 응답 시간* 세 메트릭을 측정한다.

1. **Full-context LLM (cost ceiling reference)** — 검증 도메인의 전체 코퍼스를 LLM 컨텍스트에 그대로 stuffing 한 뒤 질문. 정확도 상한의 reference 인 동시에 *비용 상한* 의 reference. 이 컬럼이 *비싸지만 정확하다* 는 점을 정량으로 보여줘야 Pareto 우월 가설의 (가) 가 측정된다.
2. **청크 벡터 RAG (대조)** — 동일 소스 셋을 청크 단위로 분할하고 임베딩한 뒤, 질문에 대해 벡터 검색으로 관련 청크 top-k 를 LLM 에 컨텍스트로 제공. *Opentology 와 비슷한 토큰/시간 비용 범위의 대조군* — 가설 (나) 가 이 컬럼과의 비교에서 측정된다.
3. **그래프 노드 RAG + 탐색 (Opentology)** — 동일 소스 셋을 Opentology 에 적재 (엔티티·관계 추출 + 노드 임베딩) 한 뒤, 벤치마크 하니스가 (a) 질문에서 anchor 키워드를 *자체 LLM 으로 추출* → (b) Opentology MCP/REST primitives 호출 (`find_entities` → `get_neighbors` / `get_subgraph` 등) 로 진입점 노드 선정 + 그래프 traversal → (c) 결과 서브그래프 + 질문을 *자체 LLM 으로 답변 생성* . *Opentology 코어는 쿼리 시점에 LLM 을 호출하지 않음* (graph primitives 만 — ADR-0006).

**Pareto 우월 검증 절차**:
- 가설 (가) 통과 조건 — (3) 의 정확도 ≥ (1) 의 정확도 (또는 통계적 차이 없음) **그리고** (3) 의 토큰/시간 ≪ (1) 의 토큰/시간.
- 가설 (나) 통과 조건 — (3) 의 정확도 > (2) 의 정확도 (통계적 유의) **그리고** (3) 의 토큰/시간이 (2) 와 비슷한 차수.

채점 방법론, 메트릭 산출, spot-check 절차, 보고서 형식은 [ADR-0005](./0005-measurement-methodology-accuracy-tokens-latency.md) 를 따른다.

### D4. 검증 도메인 — 상거래 비즈니스 규칙

검증 도메인은 **상품·카테고리·프로모션·쿠폰·재고 같은 개념이 다중 hop 관계로 얽힌 상거래 영역** 이다. 선택 근거 세 가지.

- **본인이 가장 잘 아는 도메인** — 정답 셋 작성 비용 (Q&A 30 개) 이 최저.
- **차이를 만들 만한 관계 구조가 풍부함** — 다중 hop, 동의어/별칭, cross-source 질문이 자연스럽다.
- **식별자 중심 도메인** — 상품명·SKU·쿠폰 코드 같은 식별자가 그대로 등장하므로 어휘 매칭이 강한 영역 (ADR-0003 의 BM25 결정과 정합).

### D5. 소스 셋 구성 원칙

소스는 *세 컬럼의 답변 차이가 드러나도록* 의도적으로 구성한다.

- **다중 hop 관계** — 한 문서만으로는 답이 안 나오고 여러 엔티티를 따라가야 답이 나오는 구조 (예: 상품 → 카테고리 → 적용 가능 프로모션 → 쿠폰).
- **동의어·별칭** — 같은 개념이 여러 이름으로 등장하는 상황.
- **Cross-source 질문** — 답이 단일 문서에 모이지 않고 여러 문서를 결합해야 만들어지는 질문.

### D6. Idempotent ingestion — 검증의 재현성

같은 소스를 두 번 넣어도 *같은 그래프* 가 나와야 한다. 이는 운영 기능이 아니라 *검증의 재현성* 을 위한 필수 약속이다. 같은 30 개 질문이 다른 ingestion 결과에 대해 다른 답을 만들면 측정 자체가 무너진다.

엔티티 동일성 판단 알고리즘 (이름 매칭, 임베딩 유사도, LLM judge 등) 은 *구현 설계 단계에서 결정* 한다. ADR 레벨에서는 *idempotent 동작이 약속이다* 만 명시한다.

### D7. 종료 조건

MVP 종료 시점에 3-way 비교 결과를 **한 장의 보고서** 로 정리한다. 보고서를 보고 본인이 "가설이 충분히 검증됐다" 고 판단하면 MVP 는 종료된다. 만족스럽지 않으면 — 가설을 다시 짚거나, 소스 셋 / Q&A 셋을 보강하거나, 진입점 전략 (ADR-0003) 을 조정한다.

## Considered Options

### 옵션 1 — Full-context reference 없이 청크 RAG vs Opentology 만 비교

거부. *Pareto 우월 가설의 한 축 (가) — full-context 대비 비용 우월 — 을 측정하지 못한다* . long-context LLM 의 등장 이후 "그냥 다 넣으면 되지" 라는 도전이 정당하므로, 이 도전에 *측정으로 답해야* 한다. Full-context 컬럼이 없으면 보고서는 *"청크 RAG 보다 약간 더 정확하다"* 라는 좁은 결론만 도출하게 되고, *"long-context LLM 의 비용 부담을 우회한다"* 라는 *진짜 가치 명제* 를 입증하지 못한다.

만약 이걸 택했다면, 측정 보고서가 가치 명제와 어긋나 *Opentology 의 존재 이유* 가 제3자에게 설득되지 않았을 것이다.

### 옵션 1-B — 정확도 단일 메트릭만 측정 (토큰·지연 제외)

거부. *가설 자체가 두 축이라 측정이 두 축이어야 한다* . 정확도만 보면 full-context 가 (작은 코퍼스에서는) 가장 좋게 나올 수 있고, 그러면 *"Opentology 는 가장 정확하지 않은데 왜 쓰는가"* 라는 질문에 보고서가 답하지 못한다. 토큰·지연 메트릭이 함께 있어야 *"정확도는 동등하지만 1/100 비용"* 같은 결론이 도출 가능.

만약 이걸 택했다면, 보고서가 *Opentology 의 진짜 가치 (비용)* 를 보여주지 못해 *상위 단계 의사결정* (post-MVP 진행 / 중단) 에 근거가 부족했을 것이다.

### 옵션 2 — 공개 벤치 (HotpotQA, 2WikiMultihop) 위주 검증

거부. *본인 도메인 정확도와 동떨어진 가설* 을 검증하게 된다. 공개 벤치 성적은 OSS 신뢰도에 기여하지만, "본인 상거래 도메인에서 효과가 있는가" 라는 진짜 질문에 답하지 않는다. *"내가 만든 걸 내가 먼저 쓴다"* 라는 원칙 (메모리의 user/dogfooding context) 과도 충돌한다.

만약 이걸 택했다면, 공개 벤치 점수 튜닝에 시간을 쓰고 본인 도메인 정확도는 *검증되지 않은 채* 출시 결정을 내리게 됐을 것이다.

### 옵션 3 — 정량 측정 없이 본인 체감만으로 종료

거부. *체감은 시간이 지나면 흐려진다* . "원래 이 정도였나?" 라는 의문이 6 개월 뒤에 들 때 기준점이 없다. 또한 다음 단계 (post-MVP 의 채팅·인증·확장) 를 시작하기 전에 *현재 시점의 정량 스냅샷* 이 있어야 *그 다음 변경이 정확도를 떨어뜨렸는지* 도 잴 수 있다.

만약 이걸 택했다면, post-MVP 에서 "예전 Opentology 가 더 나았던 것 같은데" 같은 회귀를 *증명할 수 없는* 상태로 운영하게 됐을 것이다.

### 옵션 4 — 다중 도메인 동시 검증 (상거래 + 사내 위키 + 연구 문헌)

거부. *MVP 범위 폭발* . 도메인마다 소스 셋과 Q&A 셋을 따로 만들어야 하고, 각 도메인의 정답 판정 기준도 다르다. MVP 의 임무는 *가설이 작동하는지* 를 *한 번* 확인하는 것이지 *어느 도메인에서 가장 잘 작동하는지* 를 비교하는 것이 아니다.

만약 이걸 택했다면, 검증 작업 자체가 별도 프로젝트 규모가 되어 MVP 종료가 무기한 늦춰졌을 것이다.

## Consequences

### 즉시 영향

- `docs/prd/1_mvp.md` 가 이 ADR 의 자매 문서로 *무엇을 만드는가* 의 사양을 담는다.
- MVP 구현은 *상거래 검증용 데이터* 가 갖춰지기 전에 *코드 골격* 을 만들고, *비교 측정* 은 둘 다 준비된 시점에 1 회 실행한다.
- 청크 벡터 RAG 베이스라인과 full-context LLM 베이스라인을 *별도의 비교 하니스* 로 구현해야 한다 (Opentology 본체에는 포함되지 않음). 위치는 `eval/` 디렉토리 — 구현 설계 단계에서 결정.
- MCQ 30 개 질문 작성이 *데이터 준비의 일부* 가 된다 (자유 서술 30 개보다 작성 시간이 1.5-2 배 — 단 채점이 자동화되므로 종합 비용은 더 낮음).

### 코드 작업 시 기억할 점

- LLM 모델 선택은 **세 컬럼이 공유** 한다. 변경 시 비교 표 전체가 무효화된다 — 측정 직전에 모델을 고정하고 변경 차단.
- 임베딩 모델은 **(2) 청크 RAG 와 (3) Opentology 가 공유** 한다 (full-context 는 임베딩을 사용하지 않음). 두 컬럼에서 *동일 모델·동일 차원* 사용을 코드에서 강제.
- LLM 호출 모든 곳에서 *usage (input/output tokens)* 응답을 로깅. 토큰 카운트는 사후에 재구성 불가.
- (3) Opentology 컬럼의 토큰은 *하니스의 anchor 추출 LLM 호출 + 하니스의 답변 생성 LLM 호출* 의 합. *Opentology 본체에서는 쿼리 시점 LLM 호출이 없음* (ADR-0006) — 임베딩 호출은 별도 항목으로 보고서에 기록.
- *Idempotent ingestion* 은 검증 재현성을 위해 필수다 (D6). 엔티티 동일성 판단 알고리즘이 바뀌어도 *결정성* 자체는 유지되어야 한다.
- 검증 도메인은 상거래로 고정 (D4). 다른 도메인으로 확장하는 결정은 별도 ADR 에서 다룬다.
- 평가 산출물은 *한 장 보고서* 다 (D7). 무거운 평가 인프라 / 게이트 / CI 통합은 *MVP 범위 밖* (ADR-0002 참고).
