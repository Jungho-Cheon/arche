# ADR-0021: bi-temporal 유효기간 데이터 모델 — 경계 확정과 단계적 도입

Status: proposed
Date: 2026-07-17

## TL;DR

지금 프리미티브 응답은 `created_at` / `updated_at` — **트랜잭션 시각**(사실이 시스템에 언제 적재/수정됐나)만 담는다. 사실의 **유효 기간**(도메인 사실이 실제로 언제부터 언제까지 참인가)이라는 축은 없다. 상거래 도메인엔 프로모션 유효기간처럼 시간에 종속된 사실이 많고, post-MVP 1순위인 코드베이스 적재도 "그 리비전 시점에 참이던 것" 을 물어야 한다.

이 ADR 은 **경계를 긋는 결정** 이다. 무거운 구축(정식 필드 승격, 시점 질의, 무효화)을 지금 하지 않는다. 대신 (1) 유효 시각(valid-time)을 운영 변경 로그(audit)와 개념적으로 가르고, (2) MVP 에서는 추출기가 유효기간을 잡았을 때 관계 속성에 예약 키로 담는 **규약만** 두며, (3) 정식 필드 승격 / `as_of` 시점 질의 / 삭제 대신 무효화는 코드 적재 ADR 과 묶어 **post-MVP 로 미룬다**.

> **valid-time (유효 시각)** — 어떤 사실이 현실에서 참이던 기간. "이 프로모션은 3/1 부터 3/14 까지 유효" 의 3/1 ~ 3/14.
>
> **transaction-time (트랜잭션 시각)** — 그 사실이 데이터베이스에 적재/수정된 기간. "이 관계는 시스템에 3/2 에 들어왔다" 의 3/2. 현재 모델의 `created_at` / `updated_at` 이 이 축이다.
>
> **bi-temporal (양시간)** — 위 두 축을 나란히 두는 모델. 정보가 바뀌면 과거 레코드를 지우지 않고 무효화(더 이상 참이 아니게 됨)해서, "지난주 화요일에 참이던 것" 같은 과거 시점 질의를 살린다. Zep/Graphiti(arXiv 2501.13956) 가 에이전트 메모리에서 이 모델로 정확도 격차를 만든 사례가 근거다.

## 이 ADR 을 읽는 이유

- Arche 가 시간에 종속된 사실(유효기간)을 어디까지 다루는지, 그 경계가 어디인지 알고 싶다면
- "왜 지금 정식 `valid_from` / `valid_to` 필드를 안 넣는가" 가 궁금하다면
- 유효 시각과 변경 이력(audit, ADR-0002 가 미룬 것)이 어떻게 다른지 확인하려면

## 읽기 전 권장 배경

- [ADR-0002 — MVP 범위 경계](./0002-mvp-scope-boundaries.md) — D5 가 "엔티티/관계 변경 이력 audit" 을 out of scope 로 뒀다. 본 ADR 은 유효 시각이 그 audit 과 *다른 개념* 임을 가른다.
- [ADR-0006 — MCP/REST 표면](./0006-mcp-rest-primitives-surface.md) — 프리미티브에 `as_of` 같은 인자를 더하는 건 표면 결정. 본 ADR 은 그 부분을 미루므로 표면을 지금 건드리지 않는다.
- [ADR-0016 — 에이전트 반복 graph-only + 정량 추출](./0016-agentic-graphonly-and-quantitative-extraction.md) — 정량(수치와 표) 인지 추출이 이미 유효기간 같은 수치를 뽑아 description/properties 에 담는다. MVP 슬라이스가 이 위에 얹힌다.

## Context — 왜 이 결정이 필요했나

### 현재 모델에 없는 축

관계 응답 모델(`Edge`)은 이미 다음을 갖는다.

- `created_at` / `updated_at` — 트랜잭션 시각 (RFC 3339 문자열).
- `properties: dict[str, Any]` — 임의 속성을 담는 열린 맵.

없는 건 **valid-time** 축이다. "이 관계가 현실에서 언제부터 언제까지 참이었나" 를 담을 자리가 계약에 명시돼 있지 않다. 상거래 검증 도메인은 이 축이 실제로 필요하다 — 프로모션/가격/계약처럼 기간이 붙은 사실이 흔하다. post-MVP 1순위인 코드베이스 적재(메모리 `project_post_mvp_code_ingest_adr`)도 버전/리비전에서 "그 시점에 참이던 호출 관계" 를 물어야 하므로 같은 축을 요구한다.

### 왜 지금 전면 구축을 하지 않나

bi-temporal 을 정식으로 넣으면 세 층을 동시에 건드린다.

1. **데이터 모델** — `Edge`(그리고 아마 `Node`)에 정식 필드 추가, 저장 표현 변경.
2. **프리미티브 계약** — `as_of` 시점 파라미터, 시점 필터 질의 의미론, 무효화된 사실의 노출 규칙.
3. **추출/적재 흐름** — 유효기간 추출 정책, 무효화(삭제 대신) 판정, idempotent 재적재와 시간축의 상호작용.

이 묶음은 검증 가설을 하나 더 늘린다("시점 질의가 정확도/토큰에 얼마나 기여하나"). ADR-0001 의 MVP 는 자연어 도메인 단발 Q&A 의 Pareto 우월 하나만 검증한다. ADR-0002 는 바로 이런 이유로 운영과 확장 기능을 절제해 미뤘다. 같은 규율을 여기에도 적용한다.

### valid-time 은 audit 가 아니다

ADR-0002 D5 는 "누가 언제 뭘 바꿨나" 의 변경 이력(audit)을 out of scope 로 뒀다. 유효 시각은 그것과 **다른 개념** 이다.

- **audit** — 운영 축. 시스템 조작의 로그. "관리자 X 가 3/2 에 이 관계를 수정".
- **valid-time** — 도메인 축. 사실 자체의 속성. "이 프로모션은 3/1 부터 3/14 까지 유효".

이 구분을 흐리면 ADR-0002 의 경계가 새는 것처럼 오해된다. 유효 시각은 도메인 데이터라 audit 미도입과 무관하게 다룰 수 있다.

## Decision — 무엇을 결정했나

### D1. valid-time 을 audit / transaction-time 과 개념적으로 가른다

유효 시각(도메인 사실이 참인 구간)은 audit(운영 변경 로그, ADR-0002 D5 가 미룸)와 다른 축이다. 트랜잭션 시각(`created_at` / `updated_at`)도 그대로 유지한다 — 유효 시각이 이 둘을 대체하지 않는다. ADR-0002 의 경계는 그대로 유효하다.

### D2. MVP 슬라이스 — 관계 속성의 예약 키 규약

추출기가 유효기간을 잡으면 `Edge.properties` 에 **예약 키** `valid_from` / `valid_to` (RFC 3339 문자열)로 담는다는 규약만 정한다.

- `properties` 는 이미 `dict[str, Any]` 라 **스키마 변경이 없다**.
- 프리미티브는 이 키를 다른 속성과 똑같이 그대로 통과시킨다. **질의 의미론을 더하지 않는다** — 시점 필터는 caller(에이전트) 가 반환된 속성을 보고 직접 한다.
- **무효화 없음** — 값이 바뀌면 기존 idempotent 적재 규칙을 그대로 따른다(같은 소스 = 같은 그래프).
- 두 키는 optional 이다. 추출이 유효기간을 못 잡은 관계엔 그냥 없다.

이 규약은 정량 추출(ADR-0016)이 이미 뽑는 수치를 **기계가독 형태로 표준화** 하는 것이고, 정식 필드로 승격하는 post-MVP 경로와 호환된다. 승격 시 이 예약 키를 정식 필드로 옮기면 되므로 전방호환을 공짜로 얻는다.

### D3. 무거운 부분은 post-MVP 로 미룬다

다음은 지금 하지 않는다.

- **정식 필드 승격** — `valid_from` / `valid_to` 를 `Edge`(및 필요 시 `Node`)의 정식 필드로.
- **`as_of` 시점 질의** — 프리미티브가 시점 파라미터를 받아 과거 스냅샷을 반환.
- **삭제 대신 무효화** — 정보가 바뀔 때 지우지 않고 유효 종료 시각을 설정.

이들은 데이터 모델 / 프리미티브 계약 / 추출 흐름을 동시에 바꾸는 결정이라 별도 ADR + 구현 이슈로 분리한다.

### D4. idempotent 와 시간축의 상호작용

MVP 슬라이스에서 `valid_from` / `valid_to` 는 추출 산물이므로 같은 소스를 두 번 넣으면 같은 값이 나온다 — 결정적이다. **무효화가 없으므로** idempotent 약속(ADR-0001 D6: 같은 소스 = 같은 그래프)을 깨지 않는다. post-MVP 에서 무효화를 도입하면 "재적재가 과거 무효화 레코드를 어떻게 다루나" 라는 새 질문이 생기는데, 그 idempotent 재정의는 무효화를 도입하는 후속 ADR 에서 함께 정한다.

### D5. 표면(ADR-0006)에 대한 영향

MVP 슬라이스는 **표면을 바꾸지 않는다** — 기존 `properties` 를 그대로 통과시킬 뿐이다. `as_of` 는 프리미티브에 인자를 더하는 표면 결정이므로, post-MVP 에서 도입할 때 ADR-0006(원자적 프리미티브만 노출, 자연어 미수용)과의 정합성을 확인한다. 시점 필터는 구조적 순회이지 답변 생성이 아니므로 ADR-0006 원칙에 부합할 것으로 보이나, 확정은 그 시점의 ADR 에서 한다.

### D6. 코드 적재 ADR 과의 선후 관계

코드베이스 적재는 post-MVP 1순위다(메모리 `project_post_mvp_code_ingest_adr`). 코드 적재는 버전/리비전에서 "그 시점에 참이던 것" 을 묻는 요구가 자연히 따라오므로, bi-temporal first-class 요구가 거기서 동시에 성숙한다. 따라서 정식 필드 승격 / `as_of` / 무효화는 **코드 적재 ADR 이후 또는 그 일부** 로 확정한다. 두 결정을 분리해 먼저 fix 하면 나중에 코드 적재의 시점 질의 요구와 어긋날 위험이 있다.

## Considered Options

### 옵션 1 — MVP 에서 first-class bi-temporal 전면 구축

거부. 데이터 모델 / 프리미티브 / 추출 계약을 동시에 바꾸는 범위 폭발이고, 검증 가설을 하나 더 늘린다(시점 질의의 정확도/토큰 기여). ADR-0002 가 운영과 확장 기능을 절제해 미룬 규율과 정면으로 어긋난다.

만약 이걸 택했다면, MVP 종료 보고서 한 장(ADR-0001 D7)이 "시점 질의를 켰을 때와 껐을 때" 라는 변수를 하나 더 풀어 해석해야 했고, 코드 적재 ADR 의 시점 요구가 성숙하기 전에 데이터 모델을 고정해 나중에 되돌리는 비용을 치렀을 것이다.

### 옵션 2 — 완전히 미룸, 규약도 두지 않음

거부에 근접했으나 미채택. 이 경우 유효기간은 추출된 자유 텍스트로만 `description` / `properties` 에 흩어져 남는다. 규약이 없으면 같은 유효기간이 관계마다 다른 키/형식으로 담겨, 나중에 정식 필드로 승격할 때 마이그레이션이 지저분해진다.

예약 키 규약(옵션 3)은 스키마 변경 없이 전방호환을 확보하는 **공짜에 가까운** 훅이라, 완전 미룸보다 이쪽을 택했다.

### 옵션 3 — 예약 키 규약 + 무거운 부분 미룸 (채택)

채택. 스키마 변경 0, 질의 의미론 0, 무효화 0 으로 경계를 지키면서, 유효기간을 기계가독 형태이면서 전방호환되게 표준화한다. post-MVP first-class 승격 경로와 자연스럽게 이어진다.

## Consequences

### 즉시 영향

- 이 ADR 자체는 **코드를 바꾸지 않는다** — 결정(규약)을 기록하는 ADR 선행 이슈다.
- 추출 프롬프트에 예약 키(`valid_from` / `valid_to`)를 실제로 반영하는 작업은 **후속 구현 이슈** 로 분리한다. 반영 전까지 유효기간은 여전히 자유 텍스트로 남을 수 있고, 그건 D2 규약의 optional 성격과 모순되지 않는다.
- ADR-0002 의 경계는 그대로다 — 유효 시각은 audit 가 아니므로 D5(변경 이력 미도입)와 충돌하지 않는다.

### 코드 작업 시 기억할 점

- `Edge.properties` 에서 `valid_from` / `valid_to` 는 **예약 키** 다. 다른 용도로 재사용하지 않는다.
- 값 형식은 RFC 3339 문자열(`created_at` / `updated_at` 과 동일 규약). 두 키는 optional — 없으면 없는 대로 둔다.
- 프리미티브 계층에 시점 필터를 임시로 끼워 넣지 않는다. 시점 질의(`as_of`)는 post-MVP 표면 결정이다.
- 무효화(유효 종료 시각 설정 후 레코드 보존)를 임시로 도입하지 않는다 — idempotent 재정의가 딸려 오므로 후속 ADR 에서 한 묶음으로.

### post-MVP 재검토 트리거

- 코드 적재 ADR 착수 시 (버전/리비전 시점 질의 요구가 동시에 성숙).
- 실측에서 `as_of` 부재가 정확도/왕복의 병목으로 확인될 시.
