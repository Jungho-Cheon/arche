# ADR-0004: 벡터 인프라 — 그래프 DB 내장 벡터 인덱스, 별도 벡터 DB 서비스 미도입

Status: accepted
Date: 2026-06-15

## TL;DR

dense 임베딩 (ADR-0003) 은 *그래프 DB 가 내장 제공하는 벡터 인덱스* 에 저장한다. Pinecone · Qdrant · Weaviate · Milvus 같은 별도 벡터 DB 서비스는 *도입하지 않는다* . 핵심 논증은 "벡터 검색 ≠ 별도 벡터 DB" — 2026 년 시점에 Neo4j 5.13+, ArangoDB, PostgreSQL+pgvector, MongoDB Atlas Vector Search 등 주류 데이터베이스가 모두 벡터 인덱스를 *내장* 한다. 도메인 확장 시 dense 신호가 더 많이 필요해질 확률 (생물학/AI 연구 등에서 50-70%) 은 *별도 서비스 필요 확률* 이 아니라 *그래프 DB 내 인덱스 활용도 증가 확률* 이다.

> **벡터 DB 서비스** — 임베딩 저장과 ANN (Approximate Nearest Neighbor) 검색을 *별도 컨테이너 / 서비스* 로 제공하는 시스템. Pinecone (SaaS), Qdrant / Weaviate / Milvus (self-host) 등.
>
> **내장 벡터 인덱스** — 그래프/관계형/문서 DB 가 *자체 인덱스 타입* 으로 벡터를 지원. 별도 서비스 없이 같은 DB 인스턴스 안에서 ANN 검색이 가능.

## 이 ADR 을 읽는 이유

- 왜 Arche 가 *별도 벡터 DB 컨테이너를 띄우지 않는지* 알고 싶다면
- 본인의 도메인이 상거래가 아닌데 (사내 위키 · 생물학 · AI 연구) Arche 가 *충분히 정확해지는지* 가 걱정된다면
- post-MVP 에 벡터 인프라가 어떻게 진화할 가능성이 있는지

## 읽기 전 권장 배경

- [ADR-0003 — 그래프 진입점 선정 전략](./0003-graph-entry-point-strategy-hybrid-lexical-dense.md) 이 *왜 dense 임베딩이 필요한가* 의 결정을 설명. 본 ADR 은 *그 임베딩을 어디에 둘 것인가* 만 다룬다.

## Context — 왜 이 결정이 필요했나

ADR-0003 은 노드 단위 dense 임베딩을 *진입점 선정의 보조 신호* 로 채택했다. 이 시점에 *임베딩을 어디에 저장할 것인가* 가 별도 결정으로 남았다. 후보 두 갈래.

- **(A) 그래프 DB 내장 인덱스** — 그래프 DB 가 노드 속성으로 벡터를 직접 저장·인덱싱.
- **(B) 별도 벡터 DB 서비스** — Pinecone / Qdrant / Weaviate / Milvus 같은 외부 서비스를 띄우고 노드 ID 동기화.

직관적으로 "벡터 검색이 필요하면 벡터 DB 가 필요하다" 는 *2022-2023 의 통념* 이 떠오르지만, 2025-2026 시점에 이 통념은 더 이상 사실이 아니다. 주류 DB 들이 벡터 인덱스를 *production-grade* 로 내장하면서, "벡터 검색 필요" 와 "벡터 DB 서비스 필요" 가 *분리된 결정* 이 됐다.

또한 사용자가 명시적으로 지적했듯 *별도 벡터 DB 의 무게* 는 단순히 "임베딩을 쓴다" 가 아니라 *별도 컨테이너 / 별도 서비스 / 데이터 동기화 부담* 에서 나온다. 이 무게가 도메인 확장 시에도 자동으로 부과되어야 하는지가 핵심 질문이다.

### 도메인 확장 시 dense 가 정말로 필요한가 — 확률 분해

상거래 외 도메인으로 확장할 때 dense 신호의 *필요 확률* 을 도메인별로 따져봤다.

| 도메인 | BM25 만으로 충분 확률 | dense 가 *결국* 필요해질 확률 | 근거 |
|---|---|---|---|
| 상거래 비즈니스 규칙 | 높음 (~85%) | 낮음 (~15%) | 식별자 중심 + LLM 별칭 추출 (ADR-0003 D3) 으로 별칭 흡수 |
| 사내 위키 / 운영 문서 | 중간 (~55%) | 중간 (~45%) | 사람·시스템·팀명은 BM25 강함. *반면* "그 배포하는 거" 같은 *지시어/암묵 표현* 이 잦으면 dense 가 유리 |
| 생물학 / 의학 | 낮음 (~30%) | 높음 (~70%) | 별칭 폭발 (BRCA1 = breast cancer 1 = ...). *단 UMLS/MeSH 같은 외부 ontology 통합 시 BM25 가 다시 강해짐* |
| AI 연구 논문 | 낮음 (~25%) | 높음 (~75%) | 매 논문이 신조어를 만들고 의역 의존도가 가장 큼. dense 의 일반화가 가장 빛남 |

평균하면 *post-MVP 도메인 확장 시 dense 가 더 많이 활용될 확률은 50-70%* . 적지 않다.

**그러나** — 이 확률은 *별도 벡터 DB 서비스 필요 확률* 이 아니다. dense 가 더 많이 활용되어도 *그래프 DB 내 인덱스 활용도가 증가할 뿐* . 데이터가 단일 DB 안에 머무는 한 별도 서비스 결정은 별개다.

## Decision — 무엇을 결정했나

### D1. dense 임베딩은 그래프 DB 내장 벡터 인덱스에 저장

별도 벡터 DB 서비스 (Pinecone / Qdrant / Weaviate / Milvus) 는 *MVP 에서 도입하지 않는다* . 그래프 DB 가 노드 속성으로 벡터를 저장하고 자체 ANN 인덱스로 조회한다.

대상 벤더 후보 (구현 단계에서 결정).

- **Neo4j 5.13+** — `db.index.vector.queryNodes` 등 native vector index. 2024-2026 운영 사례 다수.
- **ArangoDB** — multi-model 에 벡터 지원 추가.
- **PostgreSQL + pgvector + Apache AGE** — 관계형 + 그래프 + 벡터를 한 DB 에. 운영 성숙도가 가장 높지만 그래프 쪽 기능은 상대적으로 단순.
- **MongoDB Atlas + Vector Search** — 문서 모델 + 벡터. 그래프 query 는 별도 모델링 필요.

선택 제약은 *(어휘 풀텍스트 인덱스 + 벡터 인덱스 + 그래프 traversal) 셋을 모두 한 컴포넌트에서 제공* 해야 한다는 점이다 (ADR-0003 D1 의 하이브리드 진입점 선정 요구). 이 제약을 만족하는 벤더로 후보를 좁힌다.

### D2. 임베딩 모델은 *외부 서비스* (라이브러리/API), DB 와 분리

임베딩 모델 자체 (예: OpenAI text-embedding-3, BGE-M3, Cohere Embed) 는 그래프 DB 와 별개의 컴포넌트다. ADR-0001 의 검증 통제 변수 — *청크 벡터 RAG 베이스라인과 동일 모델* — 를 만족시키기 위해 *교체 가능한 어댑터* 형태로 둔다.

선택은 구현 단계 결정. 단 검증 측정 직전에 *고정* 되어야 한다.

### D3. "벡터 검색 ≠ 별도 벡터 DB" 의 분리 원칙

본 ADR 의 핵심 원칙은 *두 결정을 분리해서 다룬다* 는 것이다.

- **벡터 검색 사용 여부** — *예* (ADR-0003 에서 결정).
- **별도 벡터 DB 서비스 운영 여부** — *아니오* (본 ADR 에서 결정).

이 분리가 가능한 이유는 D1 의 내장 인덱스 옵션이 *production-ready* 이기 때문이다. 두 결정을 묶어 다루면 *벡터 검색이 필요하면 자동으로 별도 DB 필요* 라는 잘못된 결합이 된다 — 이는 2022-2023 의 인프라 상태에서나 사실이었다.

### D4. 도메인 확장 시의 진화 경로

post-MVP 에서 도메인이 확장되어 dense 활용도가 증가할 때의 진화 경로는 *세 단계* 로 명시한다.

1. **단계 1** (현재 / MVP) — 그래프 DB 내장 벡터 인덱스. 노드 단위 임베딩.
2. **단계 2** (도메인 확장 초기) — 동일 DB 의 인덱스에 *임베딩 차원 / 정밀도 / 파라미터* 조정. 별도 서비스 없음.
3. **단계 3** (대규모 / 검색 패턴 다양화) — 그래프 DB 내장 인덱스가 *진짜로 한계* 에 도달한 시점에 별도 벡터 DB 도입 검토. *단계 1, 2 의 측정 결과가 트리거* .

단계 3 은 *추정* 컨테이너 수십 개 이상 / 노드 수천만 개 이상 / 다중 벡터 (multi-vector) 검색 요구가 동시에 만족되어야 정당화된다. MVP 와 post-MVP 초기에서는 단계 1-2 로 충분하다.

## Considered Options

### 옵션 1 — 처음부터 별도 벡터 DB (Qdrant / Milvus)

거부. *MVP 의 운영 무게 / 인지 비용 / 동기화 부담을 정당화하지 않는다* . 별도 서비스는 다음을 추가한다.

- docker compose 컨테이너 한 개 추가
- 노드 ID 와 벡터 인덱스의 동기화 코드
- 백업 / 모니터링 / 보안 정책의 *두 시스템 적용*
- 데이터 일관성 (그래프 ↔ 벡터) 의 *재확인 비용*

이 무게를 가설 검증 단계에서 부과하면 *MVP 의 진짜 목적 — 가설 검증 한 번* 이 흐려진다. 별도 DB 의 이득 (대규모 ANN 성능) 은 MVP 스케일 (수천~수만 노드) 에서 의미가 없다.

만약 이걸 택했다면, 사용자 환경 (`docker compose up` 한 줄로 시작) 의 가벼움이 줄고, 데이터 동기화 버그가 *가설 검증 결과를 흐리는* 가짜 변수가 됐을 가능성이 있다.

### 옵션 2 — dense 임베딩 자체를 MVP 에서 빼고 BM25 만

거부. *범용성을 잃는다* . ADR-0003 의 거부 옵션 2 와 같은 논리. 상거래에서는 BM25 가 강하지만 *도메인 확장 시* dense 가 필요해질 확률이 50-70% 이고, MVP 에서 임베딩 슬롯을 비워두면 확장 시 *통제 변수 (ADR-0001)* 가 무너지는 마이그레이션을 해야 한다.

또한 비교 가설 자체 — 청크 벡터 RAG vs 그래프 노드 RAG — 가 *둘 다 임베딩을 사용* 하는 형태로 설계됐다. dense 를 빼면 이 통제가 깨진다.

만약 이걸 택했다면, MVP 검증은 가능하지만 *상거래에서 잘 됐다* 는 결과의 일반화 비용이 커서 post-MVP 시작 시 *진입점 전략을 갈아엎어야* 했을 것이다.

### 옵션 3 — *MVP 에서는 내장 인덱스, 도메인 확장 직전에 평가* 라는 명시 약속만

거부. 본 ADR 의 D4 와 거의 같지만, *평가 시점을 약속하지 않는 것* 만 다름. 차이는 작아 보이지만 *post-MVP 에서 별도 DB 결정을 미루는 명분* 이 약해진다.

D4 처럼 *단계별 진화 경로* 를 명시하면 *어떤 측정 결과가 트리거인지* 가 분명해져 무의미한 *언제 별도 DB 로 갈까* 토론이 줄어든다.

만약 이걸 택했다면, post-MVP 초기에 *별도 벡터 DB 도입* 이 *측정 결과에 근거 없이* 들어왔을 가능성이 있다.

## Consequences

### 즉시 영향

- 그래프 DB 선택이 *벡터 인덱스 + 어휘 풀텍스트 인덱스 + graph traversal 셋을 모두 내장 제공하는 벤더* 로 좁혀진다. Neo4j 5.13+ 가 현재 가장 강력한 후보.
- `docker-compose.yml` 에 별도 벡터 DB 컨테이너가 없다 — 그래프 DB 컨테이너 하나가 셋을 모두 담당.
- 노드 스키마에 `embedding` 속성이 *처음부터* 들어간다 (도메인 확장 시 마이그레이션 비용 0).

### 코드 작업 시 기억할 점

- 임베딩 생성 코드는 *DB 와 분리된 어댑터* 다. DB 에 박지 말고 별도 서비스 / 클라이언트로.
- 벡터 인덱스의 차원 / 거리 메트릭 (cosine / dot product / euclidean) 은 임베딩 모델 선택에 종속. 모델 교체 시 인덱스 재생성 필요 — 측정 직전 고정 후 변경 금지.
- 청크 벡터 RAG 베이스라인 코드는 *동일 임베딩 모델* 을 사용 (ADR-0001 통제 변수). 이 코드는 Arche 본체가 아니라 비교 하니스 (`examples/` 또는 `eval/`) 에 둔다.
- post-MVP 에서 별도 벡터 DB 검토를 시작할 때, *현재 단계의 측정 보고서* 가 트리거 근거다. 측정 없이 인프라 변경 금지.

### 도메인 확장 시 영향

- 사내 위키 / 연구 문헌으로 확장 시 dense 활용도가 자동 증가. 이는 *그래프 DB 내 인덱스의 부하 증가* 로 나타난다 — 별도 서비스 결정이 아니라 *동일 DB 의 튜닝* 으로 푸는 것이 첫 시도.
- 단계 3 (별도 벡터 DB 도입) 트리거는 *DB 자체 한계 도달* — 인덱스 빌드 시간, ANN latency, 메모리 사용량의 세 메트릭이 동시에 한계에 닿는 시점.
